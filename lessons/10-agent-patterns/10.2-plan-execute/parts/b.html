Level 2 · Plan-and-execute

Plan-and-execute: a plan, an executor, one replan, offline

The loop and plan_execute on the row with the manager's cap, at Rs 0.

Definition

plan_execute is a LangGraph StateGraph on the turn's context with six nodes: plan, act, tools, step, replan and solve. plan sends the question under the desk's own prompt, PLANNER and the tools' declarations written as text, and binds no tool; read_plan() keeps each numbered line of the reply as a step. Gemini 3 sometimes tries to call one of those declared tools anyway, and with none bound the reply comes back holding nothing (the call's record says finish UNEXPECTED_TOOL_CALL), its tokens billed: _ask() then asks once more, adding that no tool can run in this call, so the empty reply costs one call, not the plan. act sends the executor the question, the plan, each step done with what it returned, and the step to carry out (EXECUTOR), with the desk's %%N_TOOLS%% tools bound. tools is the ToolNode with the brains' timed wrapper that lesson 10.1's react_text uses, so check_args, the ledger and the tools' budgets are the Desk's own. step reads what came back in said_of()'s three words. A refused or failed step sends the turn to replan, at most MAX_REPLANS times a turn; its numbered reply replaces the steps not yet run, and a later refusal is kept. solve answers from every step's results, binding no tool.

What each call reads is chosen in code. The executor and the replanner read a search's handbook passages whole and its statute and guidance passages by name only (by_name()): no calculator takes a figure from a Code's text, so that text would only be read again at every step. The solver reads every passage whole, once.

Level 2 · ReWOO

ReWOO: one plan with placeholders, checked and run in waves, offline

The plan's readers on their own, then rewoo on a chained row, at Rs 0.

Definition

rewoo is a StateGraph of plan, wave, tools, collect and solve. plan sends the question under the desk's prompt, REWOO_PLANNER and the tools' declarations with extract's. read_rewoo() reads each line written #E<n> = <tool>[<JSON object>] as a step. check_rewoo() refuses the plan before any tool runs when it has no step; more steps than the turn's %%MAX_CALLS%% calls, since its tools run with no call between them and the Meter would not bound them; a tool the desk does not hold; arguments that are not one JSON object; a placeholder naming a step not written above it; an extract that reads no search; or a search's placeholder where a figure goes. A refused plan goes straight to the solver, which says why.

needs() gives what each step waits for: the steps its placeholders name, and, for a calculator, every search written above it, because a calculator reads the turn's passages. next_wave() picks every step that is ready. A wave's tool calls go on one AIMessage that code builds and never sends to a model, so ToolNode runs them side by side, as it runs one model message's calls. Its extract steps are executor calls, one after another, each sent the passages its search found (EXTRACTOR). resolve() fills each placeholder with its step's value, and check_args still checks every calculator's arguments, so a figure only the plan wrote is refused. A step whose placeholder's step was refused, failed or never ran never runs.
