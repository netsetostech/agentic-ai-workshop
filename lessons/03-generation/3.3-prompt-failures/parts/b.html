Definition

The Chat page sends your question to rag-api's /v1/stream as you, through IAP, and asks for %%UI_TOPK%% passages. Before the first token arrives, the stream sends one citation event per passage the model was given: the packed set, after the budget, which the page lists under Sources, each with its first 200 characters. The answer streams in as plain text, because a stream carries no response schema: no answerable flag, no quotes of the model's own. The gate asks /v1/query instead, for %%TOP_K%% passages and a structured reply. The model reads the same SYSTEM either way, but from a pool one passage deeper, and the gate can judge its reply field by field. So the Chat page is where a person meets a failure, and the gate is where one can be counted.

Level 3 · The kit

The prompt and the gate's rule in the kit: SYSTEM, the prompt line, row_verdict() and the passage checks

The %%N_RULES%% rules every answer starts from, the line that joins them to the passages, and the code that decides a row failed and why.

Definition

SYSTEM is a string set once in generator.py: a line saying who the model is, then %%N_RULES%% numbered rules. Rule 1 confines the answer to the numbered context, rule 2 asks for [N] markers, rule 3 is the refusal rule, rule 4 caps the length, and rule 5 says what a quote is: the clause that answers, at most twenty-five words. A sixth, DATED_RULE, is added only when a packed passage carries an effective date. None of the corpus's documents declares one, while %%N_DEMO_DATED%% rehearsal documents under evals/demo do (%%DEMO_DATED%%). So on a lane that holds the corpus alone, no golden row's prompt carries rule 6; if an earlier lesson left a dated version current, its rows' prompts on the lane do. generate() packs the passages within the budget (lesson 3.4) and builds the prompt in one line: SYSTEM, the dated rule when it applies, the context, the question.

The gate's rule has two layers. THRESHOLDS are rates over many rows, so a run can be green with rows failing: correct_rate needs %%NEED_CORRECT%% of the %%N_ANS%% answerable rows answered right, so up to %%MAX_FAIL%% can fail before that rate turns red, and refusal_rate needs %%NEED_REFUSED%% of the %%N_UNANS%% unanswerable rows refused. Those failing rows are what this lesson works from. row_verdict() is the gate's judgment of one row as a function of the reply alone: live() keeps an inline copy that lessons quote, and a test holds the two equal. Figures are compared with normalise() on both sides, so 300 and three hundred are one figure, and contains() makes a figure stand on its own: 60 is not in 160 days. Since 8 October each row's record keeps its answer and its citations, and with the switch on, quote_check() and anchors_found() run on the pool read back.

Level 4 · REST

The live eval, with every answerable row's pool read again

Every golden row asked through /v1/query, every answerable row's passages read back through /v1/passages, and every record kept in a report.

Definition

make eval-live asks every golden row through /v1/query as documind-ui-sa, which make roster put on the three golden tenants, and every isolation row again as documind-outsider-sa, which must be refused with a 403. REPORT= writes each row's record: its outcome, verdict and why, its latency and stages, the first 600 characters of its answer and its citations. DOCUMIND_EVAL_PASSAGES=1 is an environment switch, not a flag, because lessons quote main() and the recipe whole; make passes the environment straight through to the script. With it on, the eval reads each answerable row's pool again from /v1/passages: the same door, roster, retrieval and rerank, and no model call. Each citation gets a quote check, each anchor a found or not found, and two [info] lines print the totals. Neither is a threshold.
