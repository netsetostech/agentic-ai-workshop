Level 5 · Direct reads

The failing rows, read with their passages, and where each fix lives

Every record that did not pass, its answer and quotes, its anchors, the sentence of its pool that holds each figure, and its address.

Definition

The cell reads the report and nothing else of the eval's: no row is asked again. For each record that did not pass it prints the why, the question, the reply's answer and each citation with its quote check, and the anchors the switch recorded. Then it asks /v1/passages for that row's pool once more, Rs 0 and no model, and prints the sentence that holds each expected figure, matched the way the gate matches figures, with contains(). Last comes address(), the rule the desk ran in step 1. A failing row's fix is the prompt's when the reply came back well formed and either the corpus answers the row and every anchor was in the pool, or the corpus does not and the reply answered anyway; the cell names the other addresses as it goes. It ends with an export line: one row of each kind the three fixes in step 7 are written for, the first of each in the golden set's order, and a note when it found fewer than three.

Level 5 · The fix

One rule per row in the bench, with the refusal rows beside it

SYSTEM edited in memory, the failing row asked again on its own pool, the %%N_REF%% refusal rows asked beside it, and generator.py's bytes checked before and after.

Definition

make bench runs evals/prompt_bench.py in your shell. It reads each row's pool once from your lane's /v1/passages and holds it fixed, so a difference between two answers is the prompt's or the model's, never retrieval's. It imports generator.py as the service does and answers with the kit's own generate(): the same packing, prompt, schema and retry, with thinking at LOW as the API asks for it. --add-rule appends one line to SYSTEM as rule 6, in memory, for the second arm only; the kit arm answers with SYSTEM as it is. The two arms answer the same rows from the same pools, one after the other, and every answer is judged by row_verdict(). When the run ends, the kit's SYSTEM and client are put back whatever happened, and the file's bytes are compared with the bytes it started with.

Each fix asks one failing row and the %%N_REF%% refusal rows, in both arms: %%FIX_CALLS%% answers, one run each. The rule is written for a kind of failure, not for the row. It names no figure and no clause, because a rule that said "the CFO approves purchases above Rs 2,00,000" would fix lk-08 by handing it the answer, and teach the model nothing about the next row. And each rule pushes the model toward answering, or toward saying more, which is exactly what the refusal rows are there to catch.

Four verdicts are possible. Fixed, and the guard held: the kit arm failed the row, the edit arm passed it, and the edit arm refused at least as many refusal rows as the kit arm. What just happened

Three failing rows, each answered again from the pool the eval drew on, once with the kit's prompt and once with one new line, and each line tried against the %%N_REF%% questions no document answers. That is the lesson's proof: a failure read, its address found, one rule written for its kind and re-run with a guard. One run each is one draw: the interval on %%ARM_N%% answers an arm is wide, and a row that flips once has shown the rule can work, not that it always will. Nothing was deployed and no file changed. Level 5 · Why it stays in memory

Why the fix stays in memory: the served prompt is the trained prompt

SYSTEM in two files, a test that holds them equal, and what shipping a rule would take.

Definition

SYSTEM lives in two files. generator.py serves it with every answer, and evals/make_trainset.py builds the tuning set behind it (lesson 12.1), so that a tuned model is served behind the prompt it was trained behind. A test in commands/tests holds the two strings byte for byte equal, and the prompt's text is registered under a version, %%PROMPT_LABEL%%, which every usage row records. Edit SYSTEM on disk and the test fails, the tuning set no longer matches what is served, and every answer would be labelled with a version whose text it no longer is. There is one more trap: DATED_RULE numbers itself 6 in its own text, so a rule shipped as the sixth would meet a second rule 6 in every prompt with a dated passage. Shipping a prompt change is lesson 3.6's: a new version, registered, built into a candidate and gated. This lesson's rules stay where the bench put them, in memory.

Which way the guard points

The refusal rows catch a rule that makes the model answer where it must not. They cannot catch the opposite. A rule written to stop an answer to a question no document answers, such as rf-06's paternity leave, pushes toward refusing: %%RULE_REFUSE%% A rule like that can only break the rows the corpus does answer, so its guard is the answerable rows: --shape lookup,join, %%N_LITE%% rows, %%N_ANSG_CALLS%% answers across both arms, Rs %%RS_ANSG_IN%% of input and at most Rs %%RS_ANSG_CAP%%. The same holds for a failing row whose why is answered without a citation, whose rule would be %%RULE_CITE%% To see what rule 3 itself is holding up, take it out and ask the refusal rows alone: make bench PROJECT="$PROJECT" BENCH_ARGS="--shape refusal --drop-rule 3", %%N_GUARD_CALLS%% answers, Rs %%RS_GUARD_IN%% of input and at most Rs %%RS_GUARD_CAP%%.

A lane with too few prompt failures

A healthy lane may fail fewer than three rows the prompt could fix, and step 6's export line then says so. The kit's cheap model is a second source of failures on the same questions. Ask it every lookup and join row on their own pools, with the kit's prompt only: make bench PROJECT="$PROJECT" BENCH_ARGS="--shape lookup,join --model %%LITE%% --show", %%N_LITE%% answers, Rs %%RS_LITE_IN%% of input and at most Rs %%RS_LITE_CAP%%. --show prints each row's pool, so pick FAIL rows whose pools hold their clause, export them as FIX1 to FIX3 by hand, and add --model %%LITE%% to step 7's commands. The fix cell prints each report's model, so a fix measured on the cheap model says so.

What the bench cannot see

  • The dated rule. /v1/passages returns no effective date, so the bench never adds DATED_RULE. That matches every golden prompt on a lane that holds the corpus alone, and not a lane where a dated version is current.
  • Figures. It returns no media URL either, so a figure or a table is answered from its caption with no image beside the prompt. A row that asks for a figure citation is not a fair bench row.
  • The tenant's cache and a tuned model. No tenant goes with the bench's calls, so no explicit cache is attached, and a tuned endpoint is refused: it is served on a regional client, and make candidate with make eval-live judges one.
  • The Chat page. The UI streams with %%UI_TOPK%% passages and no schema; the bench answers like /v1/query, with %%TOP_K%% passages and the schema. A rule that fixes a row in the bench is a rule for /v1/query's replies first.
  • Its own rows. The bench's answers go from your shell to Gemini and never pass through rag-api, so they leave no query usage row: each run leaves one passages row per row it read, and its own printed total.

What comes next

The pool is what retrieval returned; the prompt holds what the budget packed. With the kit's chunks the two are the same: six of the corpus's largest chunks, with SYSTEM, the dated rule and the longest golden question, come to %%WORST%% tokens of the %%MAX_CTX%% allowed, and the largest golden prompt on the Rs 0 lane to %%TOK_MAX%%.
