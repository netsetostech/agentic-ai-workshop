Chain of thought in the kit: the level, the schema, the zero-shot prompt and the bench

Where the generator sets its thinking, why prompted working can only land in the answer, and how the prompt bench changes either without touching generator.py.

Definition: the generator's thinking

_call() sends one generate_content with the structured-answer config. Two of its settings are the cap and the thinking: max_output_tokens, %%MAX_ANSWER%% unless the retry asks for three times that, and thinking_level %%KIT_LEVEL%%. The comment between them says why there is no temperature, and why the kit names a level rather than a budget of zero. _usage() then bills each attempt: the thought tokens join the visible ones in tokens_out, the figure every usage row and the month's budget counter read. Definition: the answer's shape has no field for working

Definition: the generator's prompt is zero-shot

SYSTEM is five numbered rules and no example. generate() starts every prompt with it, adds DATED_RULE as a sixth rule only when a packed passage carries an effective date, then appends the packed context and the question. Nothing in it shows a solved question, and nothing asks for the working: what the model works out before it answers is left to the thinking level.

Definition: the prompt bench

evals/prompt_bench.py asks the kit's own generate() the same question at each level you name, from one fixed pool. Each row's pool is read once from your lane's /v1/passages before any answer is asked; step 5 reads one. Each answer goes through a recorder that stands in for generator._client. It sends the request as _call() built it, with the level being benched in place of %%KIT_LEVEL%%, and keeps the config as sent and the usage, the thought tokens apart from the visible ones. The kit arm at %%KIT_LEVEL%% is therefore the API's own request. A rule added with --add-rule changes generator.SYSTEM in memory for the edit arm's answers only, and the kit's text goes back after, so generator.py is never written. Every answer is judged by the eval gate's own row_verdict(), and every quote is checked against the row's pool. make bench mints the API's token as documind-ui-sa and runs the script; without make, set DOCUMIND_ID_TOKEN and GOOGLE_CLOUD_PROJECT yourself.

Level 3 · REST

The pool the bench holds fixed: /v1/passages for jn-03

The retrieval half of /v1/query and nothing after it: the passages a join's answer is written from, with no model call.

Definition

POST /v1/passages runs the same door, roster, retrieval and rerank as /v1/query, then returns the pool itself, each passage with its full text, and writes a usage row with no tokens and no cost. The bench reads each row's pool here once, with the body run_eval.ask() sends, top_k %%TOP_K%%, and every arm, level and run answers from that pool. A difference between two of its answers is then the prompt's or the model's, never retrieval's. A row whose pool comes back empty is not benched: /v1/query would refuse it with no model call.
