Level 4 · The ref clause

A branch dispatch, refused at the auth step

The same workflow, the same fork, another branch: eval-gate passes, and release-candidate stops before it can call Google as anyone.

Definition

A run started on a branch carries refs/heads/<branch> in its token's ref claim, and the provider's third clause wants %%TRUST_REF%%. So the token service refuses the exchange, and the auth step fails. documind-cd.yml's header says so in advance: a run from any other branch fails at the auth step, and that is the branch gate working, not a misconfiguration. Here is why it matters. Anyone who can push a branch to your fork can change the workflow file on that branch, and a run of that branch uses that branch's file. Without the ref clause, the rewritten workflow would get the same hour as sa-documind-cicd that main gets.

Do it: a branch, a run, a refusal

The cell makes a branch at main's commit through GitHub's REST API, dispatches the workflow on it, waits for the run to finish, prints its summary and the error lines of the failed step, and deletes the branch. In the browser: the branch menu on your fork's code page, then Run workflow with that branch chosen.

%%CELL_BRANCH%% %%OUT_BRANCH%%

eval-gate passed: it needs no credential, so the branch makes no difference to it. release-candidate failed at its auth step, with Google's refusal in the error line, and the steps after it never ran, so nothing was built and nothing was deployed. promote never started. The workflow file, the repository and the commit were step 6's; only the ref differed.

What just happened

The refusal happened at Google, before any credential existed: the token service read the branch from GitHub's signed token and found the condition false. Nothing in the branch could change that, because the token is GitHub's to sign and the branch is GitHub's to report. To deploy from another branch you would change the trust itself, which make plan refuses (step 4).

Each Google call the run makes, and what the kit grants for it

Read the candidate path's calls against sa-documind-cicd's roles, the APIs make apis enables and the two grants make build-access adds:

%%CALLS_TABLE%% @@mk_build@@ @@cb_logging@@

None of the %%N_ROLES_W%% roles is a Cloud Storage role, and none reads logs, on purpose. gcloud builds submit uploads the source to the project's Cloud Build bucket before the build starts. Left to choose that bucket, it lists the project's buckets to check the bucket is the project's own, which needs a project-wide storage permission. The workflow names the bucket instead, and make build-access, which make up runs, gives the account the bucket's legacy writer role on that one bucket. Following the build's log would mean reading Cloud Logging, so the step submits the build --async and polls its status, printing a link to the log. Cloud Build runs the build as the project's default compute account, and with Google's default organization policy the account that submits a build must be able to act as that account: make build-access grants that too, and refuses on a project whose default account holds Editor or Owner, where acting as it would hand the pipeline the same. sts.googleapis.com, the token service, is among the %%N_APIS%% APIs make apis enables.
