Three places to run an eval, and what each one can see

The same golden set in CI, on a candidate and among live traffic, and the failures each place catches first.

Where an eval runs decides what it can catch. The kit runs one golden set in three places, and they are not interchangeable. In CI, on every push, the offline gate reads the %%N_ROWS%% rows and the corpus beside them. It needs no credential and never calls the model, so all it can judge is the set itself. Before a release, the candidate gate sends every row to a revision of the API that takes no traffic, reads every reply, and holds the release on %%N_THRESHOLDS%% thresholds and %%N_REQ%% required rows. After the release, nothing gates. Every answer leaves one usage row, and two alert policies read rates from the rows. They can open an incident, but they cannot stop anything.

Each place sees more traffic and less of each answer. CI reads no answer at all. The candidate gate reads %%N_ROWS%% answers word for word, but only answers to the set's own questions, and only through /v1/query. Live traffic is every question anyone asks, but its row keeps counts, clocks and flags, never the question or the answer. So the later a failure is first caught, the more people met it first. Some failures are caught nowhere, and the matrix below names them.

The judge sits beside the pipeline, not in it. Lesson 4.2's judge can read any deployment's answers, a candidate's included. No step of either workflow runs it, and its exit code does not depend on its scores. It explains what the gate found, and it never decides.

🏭

A factory that makes pressure cookers. Incoming-material inspection checks the steel and the test gauges before a single cooker is made: is each gauge calibrated, can each specification be met at all? It never tests a cooker. Before a batch ships, the pre-shipment test takes the batch off the line and pressure-tests every unit against the specification, and one failure holds the whole batch. After the cookers are sold, the warranty desk hears from every city, but only as counts: so many returns from Pune this week. It never sees the cooker that leaked quietly and was never returned. CI is the incoming inspection, the candidate gate is the pre-shipment test, and the usage rows and alerts are the warranty desk.

What the matrix is not

It calls no API and runs no model. The stub's replies fail one way each, and a real failure is rarely that clean. The live column says whether a policy can see the failure at all, not how much traffic it takes to stay above %%UNANS_T%% for %%UNANS_MIN%% minutes: that depends on how many good answers the same tenant gets in the same windows.

One distinction to hold: a gate blocks and an alert notifies. A gate runs before anyone is affected, and its exit code can stop the change. An alert runs on traffic people are already sending, and all it can do is tell someone.
