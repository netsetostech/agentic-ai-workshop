Two workflows, the same line of Python in each, the order their jobs run in, and a row broken on purpose.

Definition

The learner kit carries two workflows. documind-dryrun.yml runs on every push and pull request, with no Google credential: every Python file compiles, the offline suites run, Terraform validates, the images build, and the last step is the offline gate. Level 3 · The candidate gate

The candidate gate: a revision with no traffic, judged before any user meets it

The release path's own checks, a candidate made with no change, the gate on its tag URL, its required rows, and the tag removed.

Definition

In documind-cd.yml the release path runs in a fixed order. make build makes the API's image, tagged with the commit. make release-candidate puts that image on a revision with no traffic and the tag candidate, and records the revision's name. A step then checks that the candidate answers as the tag: its /version must name the sha being released, or the gate would judge some other revision. make eval-live judges the candidate's tag URL with tokens minted for the service's canonical URL, because the API checks every token against that URL and refuses one minted for the tag. Only a green gate lets promote start, and promote waits for the reviewers of the production environment before it moves traffic to the recorded revision, by name.

On your lane, make candidate makes the same kind of revision without a build: a new revision from the service's latest one, the image unchanged, with %%N_SETTINGS%% settings written over it. With no override it writes the Makefile's defaults, which are the values make up deployed the API with, unless your shell exports one of them (lesson 4.4 diffs the two revisions to prove it). So this candidate runs what the live revision runs, and the gate's verdict on it is the release decision for "no change". The verdict has three parts: the %%N_THRESHOLDS%% rates against their thresholds, each of the %%N_REQ%% rows in required.json passing on its own, and no leak. Exit 0 lets the release go to a person. Exit 1 or 2 fails the job, and promote never starts.

What just happened

It is also the placement that costs, because every row is a model call. And it sees only what it asks: %%N_ROWS%% questions, through /v1/query, as the eval identity. A failure in other questions, in the stream, or in traffic it never sends is out of its reach. Step 5 turns to that traffic.

Level 4 · Live traffic

Live traffic: the usage rows, and the gate's rows among them

One question in the UI, the row every answer leaves, the log split by revision and by caller, and make usage.

Definition

After the flip there is no gate. What live traffic leaves is one usage row per answer, logged by rag-api as structured JSON, which Cloud Logging stores with the revision that wrote it. The row carries the tenant, the caller, the tokens and rupees, the three stage clocks, the pool, the confidence and an unanswerable flag: %%N_ROW_FIELDS%% fields, and none of them is the question or the answer. Nothing that reads the rows can tell a right answer from a wrong one; what it can count are rates. The gate's rows land in the same log. They carry the eval identity, documind-ui-sa, where a person in the UI carries their own email, and the candidate's rows carry the candidate's revision name. make usage reads the same rows but keeps only the payload, so its tables group by tenant, model, brain, surface and backend, never by revision or caller.
