Level 6 · The burst

The burst: %%N_OBJECTS_W%% objects against %%SQUEEZE_W%% instances

The worker's ceiling cut from %%MAXI_W%% to %%SQUEEZE_W%%, the kit's corpus uploaded again, and the bus's response read in the request log and in Pub/Sub's own metrics. Then the ceiling put back.

Why squeeze. A bus that pushes has to learn how fast its reader can go, and it learns only from the answers. Pub/Sub starts a subscription's push window small, widens it with each success and narrows it with each failure (Google's push page). Cloud Run holds a request that finds no free instance in its pending queue and then refuses it with a 429. The subscription counts each refusal as a failed delivery, retries it after the backoff, and charges it against the %%ATTEMPTS%% attempts; the comment in step 4's subscription is the kit's record of a first live load that learned this the hard way. At %%IN_FLIGHT%% in flight, %%N_OBJECTS%% messages are %%ROUNDS_FULL%% rounds of work; at %%SQUEEZE%% they are at least %%ROUNDS_SQ%%, and they have to queue. Squeezing the ceiling makes the reader the bottleneck, so you can watch the bus adapt to it.

Why the corpus. make ingest-corpus uploads the kit's corpus again: by upload.sh's rule, %%N_ACME%% objects for acme, %%N_GLOBEX%% for globex and %%N_ZETA%% for zeta, %%N_OBJECTS%% in all. Each upload is a new generation, so each fires a notice, and each notice is pushed until the worker takes it. But the bytes are the ones your lane indexed when it was built, so every claim is already taken: the worker downloads the generation, hashes it, finds the claim and answers 200 duplicate. Nothing is parsed, nothing is embedded and no model is called. The burst costs deliveries and nothing else, as long as that "every" holds, and the first cell checks it before anything moves:

@@upload_rule@@ %%CELL_PRECHECK%% %%OUT_PRECHECK%%

The cell applies upload.sh's rule to your clone, hashes every file it would upload, and compares each hash with the ledger row for that object. A file that differs is a version your lane does not hold as current. The burst would index it, at its usual cost, and if its bytes are a version the ledger retired, it would make that old version current again. Lessons 1.6 and 6.3 put the handbook back at their ends, so on a lane that followed them every file matches. If one does not, stop here and find out why before you go on. A clone checked out on Windows with line-ending conversion, for example, turns every Markdown file into new bytes.

Squeeze, then upload

Google recommends a service-level maximum for most uses, which needs no new revision (its maximum-instances page); the revision's flag is used here so that the restore at the end puts back exactly what the kit deployed.

upload.sh's closing lines are older than the kit's path. There is no Eventarc trigger (step 4's notice replaced it), and the pull it suggests would acknowledge, and so delete, whatever the dead-letter subscription holds. Use make dlq, which only looks. What the worker saw

Give it two minutes, then read every request Cloud Run received for the worker since BURST_SINCE, by status and by ten-second slice, with the worker's verdicts for the same window:

%%CELL_BURST_LOG%% %%OUT_BURST_LOG%%

Three things to check in your output. First, every object was taken in the end: the 200s add up to %%N_OBJECTS%%, and the verdicts say ingest_duplicate as many times. One more of each is a redelivery, which at-least-once allows and the claim makes harmless. Second, each 429, if you have any, is a delivery Cloud Run refused before the worker saw it, so it has no worker line beside it. The retry policy holds that message back for at least the %%MIN_BO%%-second minimum before delivering it again (best effort, in Google's words), which is why the 200s spread into later slices. Third, the duplicates are invisible to the kit's lifecycle metric, which counts only %%N_COUNTED_W%% of the worker's verdicts:

@@events_metric@@

The metric counts %%COUNTED%%. ingest_duplicate is not among them, so a burst of %%N_OBJECTS%% deliveries moves documind/ingest_events by nothing at all. To count deliveries you need the request log, as above, or Pub/Sub's own metrics, next.

What Pub/Sub saw

Pub/Sub keeps its own counts for each subscription: the backlog (messages not yet acknowledged), the age of the oldest of them, and every push it made, by how the push ended. Cloud Run counts its instances the same way. These metrics are sampled every %%SAMPLE_S%% seconds and can take up to %%VISIBLE_S%% seconds to appear (Google's list of metrics), so run this cell at least three minutes after the upload:

%%CELL_BURST_METRICS%% %%OUT_BURST_METRICS%%

The backlog column is the queue's version of what Kafka calls consumer lag: messages published and not yet dealt with. The age of the oldest one is the number an operator pages on, because it grows when the reader is stuck however small the backlog is. The push columns are Pub/Sub's side of the request log: ack for every 2xx, 4xx for every 429 that Cloud Run sent back. The instance column should stay at %%SQUEEZE%% or under, though Google notes that a spike can take a service past its ceiling for a brief period, so one minute at a little over %%SQUEEZE%% is not a failure of the squeeze. The last two lines are the proof that the burst did no harm: nothing was forwarded to %%DLQ_TOPIC%%, and %%DLQ_SUB%% holds nothing, because no message came near %%ATTEMPTS%% refusals.

Notice what the kit itself would have told you about this burst: nothing, and rightly. It has two alerts on this path. One watches %%DLQ_SUB%%. The other, since 13 October 2026, watches %%SUB%%'s oldest unacknowledged message and pages when it stays over %%BACKLOG_MIN%% minutes for %%BACKLOG_FOR_MIN%% minutes, so a worker stuck at its ceiling, or down, shows up there about half an hour in, rather than when messages start reaching the dead-letter topic after their twelfth refusal, about an hour after the first by lesson 1.5's clock. A burst that clears in a few minutes, like this one, pages neither. Lesson 8.4 sets that threshold against the slowest turn one document can honestly take.

Put the ceiling back

%%CELL_RESTORE%% %%OUT_RESTORE%%

The revision is back at %%MAXI%%, the value lesson-12.5.sh holds. The next make deploy-services would write it again in any case, because the script, not the revision, is the source. make dlq looks at the dead-letter subscription without acknowledging anything, and an empty list is the result you want.

The same burst on Kafka. Five consumers in one group, reading a topic of at least five partitions, would each pull at their own pace. Nothing would be refused and nothing would count against a ceiling of attempts; the backlog would show as lag that rises and falls. That is the real difference between push and pull. On a pushing bus a full reader refuses, and each refusal spends a budget that ends in the dead-letter topic. On a pulling bus a full reader simply reads later, until the records outlive their retention.

Level 6 · Kafka

Pub/Sub mapped to Kafka: thirteen rows, and when Kafka would be the better bus

Every setting this page has read, set beside Kafka's nearest concept with the gap between them; then the kit's reasons for its choice, and the point where they stop holding.

Each row starts from what your lane does, as steps 4 to 7 read it, and names Kafka's nearest concept. Kafka's side is its general model and its documented defaults. Pub/Sub's side is the kit's Terraform and Google's documentation, read on %%READ_ON%% and linked under the table.

%%KAFKA_TABLE%%

Google's pages behind the Pub/Sub column: %%SOURCES%%.

Why the kit's choice holds

Read the last column for what the kit would lose by moving, and almost every gap turns out to be covered by something outside the bus. Duplicates are covered by the claim on the content hash, and order by the generation guard, which acknowledges a late notice as stale (both in step 4). Replay is covered by the versioned bucket, which the nightly walk, and make restore, replay from by rewriting an object onto itself:

@@rewrite@@

That is the deepest point of the mapping. On Kafka the log is the record of what happened, and replay means moving an offset back along it. In the kit the bucket is the record: every generation of every object, kept by versioning. The bus is only the doorbell, and a doorbell that forgets is fine when the house keeps the parcels.

When Kafka would be the better bus

  • A second reader that needs the history. An audit consumer, or a pipeline that re-embeds the corpus with a new model, wants every event from the beginning. On Kafka that is a new consumer group set to start from the earliest retained record. On Pub/Sub a new subscription receives only messages published after it exists, so the kit would rewrite every object, or run the walk, to make the events again.
  • Order per key. Kafka keeps a partition's records in order, and a key always maps to the same partition, so a consumer that retries a record before it moves on keeps the order. Pub/Sub orders only with ordering keys, which the publisher (here Cloud Storage) would have to set on every notice; a push subscription then holds one outstanding message per key.
  • The events as the record. If the events themselves must be kept for longer than %%RET_MAX%% days, Pub/Sub's longest retention, or for good, then a log is the store, and on Kafka retention is one topic setting.
  • Backpressure without a budget. Step 7's burst: a pulling reader that falls behind lags, while a pushed one refuses and spends attempts. A worker whose documents take minutes each, on a corpus of millions (lesson 8.3's arithmetic), lives better with lag than with a countdown to the dead-letter topic.
  • The stream itself as the work. Joins, windows and running totals over the events are what Kafka Streams is built for, reading the same log; a Pub/Sub subscription hands each message to its reader once and then forgets it.

Before any of those, look at what Pub/Sub can do without Kafka. Topic retention (up to %%RET_MAX%% days) with seek gives replay. A pull subscriber reads at its own pace, and a pull subscription can have exactly-once delivery. Ordering keys give per-key order. Each is one setting in eventarc.tf and one change in the worker. Google Cloud also runs Kafka for you, as Managed Service for Apache Kafka: that takes the brokers off your on-call rota, but not the consumer code, the retry topics or the dead-letter topic, which a subscription gives the kit for nothing. For this lane the threshold is plain. While the bucket is the record and one worker is the only reader, the doorbell is enough; the day a second team needs to replay the events at its own pace, the log has earned its brokers.
