Level 0 · Theory

The three phases: setup, Terraform, build and deploy

What happens where, and why in this order.

Standing up a lane is three jobs, and each one needs what the one before it produced. Every block on this page runs in the same Cloud Shell terminal, and every block ends in a checkpoint: a PASS line, or a STOP line that names what to fix.

1

Setup

The project and billing, the tools, Python 3.12 and a clone of the kit. Settings go into one file so a new terminal can restore them.

~/rag-env.sh
2

Terraform

APIs, the state bucket, a saved plan you read, then the apply. Every resource the services need exists afterwards; no service runs yet.

terraform apply <plan>
3

Build and deploy

Pin the commit, build seven images under that tag, deploy each to Cloud Run as its own account, then write the rosters.

GIT_SHA

Setup changes almost nothing in your project. It makes Cloud Shell ready: the project selected, a Python 3.12 environment outside the source tree, and the kit cloned from main into ~/deploy_module_rag. The values every later command needs (project, region, residency, bucket names) are saved to ~/rag-env.sh, which is what lets you close the tab and continue tomorrow.

Terraform compares what the kit declares under terraform/ with what your project has, writes the difference to a saved plan, and applies exactly that plan. Its record of what exists, the state, lives in a versioned bucket in your own project.

Build and deploy starts by pinning GIT_SHA: the one commit every image is built from and every service is deployed with. Cloud Build turns each service into an image tagged with it; gcloud run deploy runs each image as its own service account. The last step writes the rosters: IAP decides who may open the page, the roster decides which tenant's documents they may ask about.

🏗

Opening a branch office. Setup is collecting the drawings and filling in the site diary, so the next shift knows where things stand. Terraform is the builder: a signed list of every wall and door before work starts, and the site register kept in the office safe. Build and deploy is moving the staff in, every one hired from the same printed staff list (the pinned commit), each with their own ID card, and a receptionist (IAP) at the door with the tenant list (the roster) in hand.

Paste long blocks carefully

Some terminals drop or reorder characters when a long block is pasted. Use the copy button on each window, never select by hand, and make sure no line ends in a backslash followed by a space. Phase 1 · Setup · S6

Get all files from the latest main

The kit from main into ~/deploy_module_rag, and the commit it is at.

Clones main into $DEMO_ROOT the first time and fast-forwards to the latest main afterwards.

Stop and read

Once you have built images in Build and deploy, they are tied to the commit saved in GIT_SHA. Pulling newer code afterwards does not change the running services; Step 18 will notice the difference and tell you to either go back to the saved commit or rebuild every image.

bash - Clone or update
# Always the latest main of netsetostech/agentic-ai-workshop-learner.
export RAG_REPO_URL='https://github.com/netsetostech/agentic-ai-workshop-learner.git'
export DEMO_ROOT="${DEMO_ROOT:-$HOME/deploy_module_rag}"
(
  set -euo pipefail
  if [ -d "$DEMO_ROOT/.git" ]; then
    case "$(git -C "$DEMO_ROOT" remote get-url origin)" in
      "$RAG_REPO_URL"|https://github.com/netsetostech/agentic-ai-workshop-learner|git@github.com:netsetostech/agentic-ai-workshop-learner.git) ;;
      *) echo "STOP: $DEMO_ROOT is a clone of a different repository. Move it aside first." >&2; exit 1 ;;
    esac
    git -C "$DEMO_ROOT" fetch origin main
    git -C "$DEMO_ROOT" checkout main
    git -C "$DEMO_ROOT" merge --ff-only origin/main
  elif [ -e "$DEMO_ROOT" ] && [ -n "$(ls -A "$DEMO_ROOT")" ]; then
    echo "STOP: $DEMO_ROOT already has files but is not a Git clone. Move it aside, then rerun." >&2; exit 1
  else
    git clone --branch main "$RAG_REPO_URL" "$DEMO_ROOT"
  fi
  git -C "$DEMO_ROOT" log -1 --format='PASS: up to date with origin/main (%h, %cr): %s'
  printf 'Commit: %s\nFiles: %s\n' "$(git -C "$DEMO_ROOT" rev-parse HEAD)" "$(git -C "$DEMO_ROOT" ls-files | wc -l)"
  if [ -n "${GIT_SHA:-}" ] && [ "$GIT_SHA" != "$(git -C "$DEMO_ROOT" rev-parse HEAD)" ]; then
    echo "NOTE: your images were built from $GIT_SHA, which is not this commit. See step 18 of the runbook."
  fi
) && cd "$DEMO_ROOT"
Checkpoint

Ends with PASS: up to date with origin/main, the full commit and the file count (1,082 on 8 October 2026).

If Git refuses to update because you edited a tracked file, commit or discard that change and rerun. Files Terraform writes (for example terraform/.terraform.lock.hcl) do not block the update.

bash - APIs and state bucket
(
set -euo pipefail
: "${PROJECT:?Restore ~/rag-env.sh}" "${PROJECT_NUMBER:?Restore ~/rag-env.sh}" "${REGION:?Restore ~/rag-env.sh}"
: "${DEMO_ROOT:?Restore ~/rag-env.sh}" "${TFSTATE_BUCKET:?Restore ~/rag-env.sh}"
cd "$DEMO_ROOT"
# The repository's API list (40 services, two batches) from commands/lesson-12.1.sh.
api_block="$(sed -n '/^# ---- ENABLE_APIS ----/,/^# ---- APPLY ----/p' commands/lesson-12.1.sh | sed '/^# ----/d')"
[[ -n "$api_block" ]] || { echo 'STOP: ENABLE_APIS block not found in commands/lesson-12.1.sh.' >&2; exit 1; }
sh -ec "$api_block"
# Two the full Terraform also needs that are not in that list.
gcloud services enable iam.googleapis.com sts.googleapis.com --project="$PROJECT"
# Google-managed service agents Terraform grants roles to.
for svc in pubsub.googleapis.com aiplatform.googleapis.com clouddeploy.googleapis.com cloudbuild.googleapis.com; do
  gcloud beta services identity create --service="$svc" --project="$PROJECT"
done
gcloud storage service-agent --project="$PROJECT"
# off.tf reads the Compute Engine default service account; it must exist and be enabled.
gcloud iam service-accounts describe "$PROJECT_NUMBER-compute@developer.gserviceaccount.com" \
  --project="$PROJECT" --format='yaml(email,disabled)'
# Terraform state bucket: reuse it if it exists, create it only if it is really absent.
if out="$(gcloud storage buckets describe "gs://$TFSTATE_BUCKET" --project="$PROJECT" --format='value(name)' 2>&1)"; then
  echo "REUSE: gs://$TFSTATE_BUCKET already exists"
elif grep -qiE 'not found|404' <<<"$out"; then
  gcloud storage buckets create "gs://$TFSTATE_BUCKET" --project="$PROJECT" \
    --location="$REGION" --uniform-bucket-level-access --public-access-prevention
else
  printf '%s\n' "$out" >&2
  echo 'STOP: bucket lookup failed for a reason other than not-found. Fix access first.' >&2
  exit 1
fi
gcloud storage buckets update "gs://$TFSTATE_BUCKET" --versioning
echo 'PASS: APIs, service agents and state bucket ready.'
)
Checkpoint

Ends with PASS: APIs, service agents and state bucket ready. If gcloud beta asks to install a component, accept it.

The state bucket is only created when the lookup says it does not exist; before, any failed lookup (such as a permission error) was treated as “absent” and a create was attempted. rag_pin_snapshot() {
  : "${DEMO_ROOT:?Run the restore block first}"

    echo 'STOP: ~/rag-save-env.sh does not save GIT_SHA. Rerun the "Save settings" block from step 5 (S3), then rerun this block.' >&2

  }
  local head dirty
  head="$(git -C "$DEMO_ROOT" rev-parse --verify 'HEAD^{commit}')" || return

  if [[ -n "$dirty" ]]; then

    return 1
  fi
  if [[ -z "${GIT_SHA:-}" ]]; then
    export GIT_SHA="$head"
    echo "PINNED: GIT_SHA set to the checked-out commit."
  elif [[ "$GIT_SHA" != "$head" ]]; then
    printf 'STOP: saved GIT_SHA %s is not the checked-out commit %s.\n' "$GIT_SHA" "$head" >&2
    printf 'Choose one: keep the built images (git -C "$DEMO_ROOT" checkout --detach "$GIT_SHA"), or adopt the new code (unset GIT_SHA, rerun this block, then rebuild every image in F3).\n' >&2
    return 1
  else
    echo "PASS: GIT_SHA matches the checked-out commit."
  fi
  git -C "$DEMO_ROOT" log -1 --format='Snapshot: %H (%cd) %s' "$GIT_SHA" &&
  source "$HOME/rag-save-env.sh"
}

def roster_plan(project: str, tenant: str, members: list[str]) -> tuple[list[tuple[str, str]], list[tuple[str, str]]]:
    """What make roster does, as data: (tenant, email) memberships and (tenant, data_region) policies.

    The members go on TENANT's roster. The UI's service account is the bearer identity of make smoke and make eval-live
    (shared/iap.py's other leg; 12.2's SMOKE note), so it sits on the three golden tenants; the MCP server's account (7.2)
    retrieves for the agent that called it and the API checks ITS email on the roster like any other caller; the chat
    service's account (12.8) is a surface like the UI's; the A2A peer's account (8.4) sits on ONE roster, acme. The
    demo's data-region policies (13 September 2026, evening): acme and zeta may be mirrored into the managed stores
    and read from them; globex's text never leaves the kit's own rows."""
    sa = lambda name: f"documind-{name}-sa@{project}.iam.gserviceaccount.com"  # noqa: E731
    plan = [(tenant, m) for m in members]
    for name in ("ui", "mcp", "chat"):
        plan += [(t, sa(name)) for t in GOLDEN_TENANTS]
    plan.append(("acme", sa("agent")))
    policies = [("acme", "any"), ("zeta", "any"), ("globex", "in")]
    return plan, policies

So the UI, MCP and chat accounts go on all three golden tenants (acme, zeta and globex), the A2A agent's account on acme only, and the policies become acme any, zeta any, globex in.
