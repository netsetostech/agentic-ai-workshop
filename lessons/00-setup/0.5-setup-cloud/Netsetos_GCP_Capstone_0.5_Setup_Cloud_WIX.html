Level 0 · Theory

The three phases: copy, create, deploy

What happens where, and why it happens in this order.

Standing up a lane is three different jobs done by three different tools, and the order matters because each one needs what the one before it produced.

1

Copy

git puts the kit, every service, the Terraform and the Makefile, in your Cloud Shell home directory. Nothing in your project changes.

~/deploy_module_rag
2

Create

Terraform reads terraform/, plans every resource, and creates them: accounts, buckets, Firestore, Vector Search, SQL, Spanner, network, alerts.

make plan
3

Deploy

Cloud Build turns each service into an image; gcloud deploys each image to Cloud Run as its own account; the UI goes behind IAP.

make up

Copy is local and free. The kit is a folder of code: the services under services/, the infrastructure under terraform/, and a Makefile whose targets drive everything else. Cloud Shell is the place to keep it because it already has gcloud, terraform, make, git and Python, it is already signed in as you, and its home directory survives between sessions.

Create is Terraform's job. Terraform compares what the kit declares with what your project already has, writes down the difference as a plan, and, once you approve it, makes the project match. The kit wraps this in a guard: make plan saves the plan and checks it, refusing any plan that would delete or replace a resource, and make up applies only that saved, checked plan. Terraform records what it created in a state file, which the kit keeps in a bucket in your own project so a new Cloud Shell session, or a teammate, sees the same lane.

Deploy starts where Terraform stops. Terraform creates the places services will run and the accounts they will run as; it does not build code. After the apply, make up continues with Cloud Build, which turns each service's source into an image in Artifact Registry, then a gcloud script per service that deploys it to Cloud Run with its flags, its account and its environment, then the steps that make the lane usable: the vector indexes ready, the roster written, the managed stores, the BigQuery view.

🏗

Opening a branch office. Copying the kit is collecting the architect's drawings and the fit-out manual into your bag. Terraform is the builder who reads the drawings, shows you a signed list of every wall and door before starting, and keeps the site register (the state) in the office safe so the next builder knows what is already there. The deploy is moving the staff in: each one with their own ID card, at their own desk, with a receptionist (IAP) at the front door who only lets in people on the list.

Before you run anything: open Cloud Shell and keep it alive

Open the Google Cloud console signed in as the account that owns your billing account, and click Activate Cloud Shell in the top bar. When the terminal opens, start a tmux session. make up runs for a long time, and Cloud Shell drops idle browser connections; inside tmux the command keeps running and you reattach to it.

bash - Cloud Shell, once per session
tmux new -s documind            # later, after a disconnect: tmux attach -t documind
gcloud --version | head -n 1
gcloud config get-value account
terraform version | head -n 1; make --version | head -n 1; git --version
python3 --version

If the Cloud Shell machine itself is recycled, after a long idle period, tmux is gone but your home directory is not: the kit, its virtual environment and Terraform's saved inputs are still there. Reattach with a new tmux session and run the session block of step 5 again.

Phase 1 · Copy

Phase 1: copy the kit into Cloud Shell

One clone, one virtual environment, the right Terraform.

The kit is published as its own public repository, and every command in the course expects it at ~/deploy_module_rag. Clone it once; afterwards a git pull brings every update. If the directory already exists from an earlier session, the block pulls instead of cloning, so it is safe to run again.

bash - Cloud Shell: get the kit
export DEMO_ROOT="$HOME/deploy_module_rag" KIT_REPO=https://github.com/netsetos/agents_workshop_learner.git
if [ ! -d "$DEMO_ROOT" ]; then git clone -q "$KIT_REPO" "$DEMO_ROOT"
else git -C "$DEMO_ROOT" pull -q --ff-only; fi
cd "$DEMO_ROOT" && git log -1 --format='kit %h, %cd' --date=short
ls
expected - the kit's top levelread only
kit COMMIT, YYYY-MM-DD
INDEX.md  INDEXING.md  INFRASTRUCTURE.md  Makefile  README.md  UNOWNED.md  cloudbuild.yaml  commands  evals
extract_documind.py  gke  mk  operators  run-service.yaml  services  shared  smoke  terraform  validate.py  workshop_demos

Write the commit down with your notes. If something behaves differently from this page later, the commit says which version of the kit you ran.

Next, the operator environment: a Python virtual environment the Makefile's Python steps use, with the kit's pinned packages, and a Terraform new enough for the kit's backend (1.9 or newer). The kit ships a helper script with one function for each.

bash - Cloud Shell: the operator venv and Terraform
cd "$DEMO_ROOT"
[ -d "$HOME/rag-shell-venv" ] || python3 -m venv "$HOME/rag-shell-venv"
source "$HOME/rag-shell-venv/bin/activate" && python --version
source commands/session-restart.sh
rag_install_python_dependencies
rag_require_terraform
terraform version | head -n 1

Before you spend anything, run the offline check. It compiles every service, checks every Dockerfile and dependency pin, and validates the Terraform, all without touching a project. If this is red, a live deploy will not be green either.

bash - Cloud Shell: the offline dry run, Rs 0
cd "$DEMO_ROOT" && make dryrun

Phase 2 · Create

A project, billing and a budget

A project made for the course, so tearing it down later touches nothing else.

Lesson 0.1 explains this step in full. In short: list your billing accounts, pick the open one, create a project whose ID starts with documind-ai-, and link it. Project IDs are global, 6 to 30 characters, lower case, digits and hyphens, starting with a letter; add your initials and a number to make yours unique.

bash - Cloud Shell: create the project and link billing
gcloud billing accounts list
export BILLING=XXXXXX-XXXXXX-XXXXXX     # yours: the ACCOUNT_ID of the OPEN account above
export PROJECT=documind-ai-YOUR-ID      # yours: unique, starts with documind-ai-
gcloud projects create "$PROJECT" --name="DocuMind lane" --set-as-default
gcloud billing projects link "$PROJECT" --billing-account="$BILLING"

Then set the budget, in the console, before anything bills: Billing → Budgets & alerts → Create budget, scoped to this project, with alerts at 50, 90 and 100 percent sent to you. A budget does not stop spending; it tells you. Step 13 is what stops it.

Phase 2 · Create

The session block: one set of variables for every command

Run it now, and again in every new Cloud Shell session.

Every command from here on reads the same handful of variables: the project, the region the services run in, your address (the person IAP will let in and the first name on the roster), the state bucket and its prefix, and the project number that appears in every Cloud Run URL. The block sets them all from gcloud's own configuration, so after a restart it puts you back exactly where you were.

bash - Cloud Shell: the session block, once per session
export DEMO_ROOT="$HOME/deploy_module_rag"
cd "$DEMO_ROOT" && source "$HOME/rag-shell-venv/bin/activate"
gcloud config set project "${PROJECT:-$(gcloud config get-value project 2>/dev/null)}"
gcloud config set run/region asia-south1
export PROJECT="$(gcloud config get-value project 2>/dev/null)"
export REGION="$(gcloud config get-value run/region 2>/dev/null)"; export REGION="${REGION:-asia-south1}"
export ME="$(gcloud config get-value account 2>/dev/null)"
export ADMIN_EMAILS="$ME" TENANT=acme
export TFSTATE_BUCKET="$PROJECT-tfstate" TFSTATE_PREFIX="documind/$PROJECT"
export NUMBER="$(gcloud projects describe "$PROJECT" --format='value(projectNumber)')"
echo "PROJECT=$PROJECT REGION=$REGION NUMBER=$NUMBER ME=$ME"
echo "state: gs://$TFSTATE_BUCKET/$TFSTATE_PREFIX"

The region is asia-south1, Mumbai, as the rest of the course uses. Pass it to every make command: the Makefile's own default is us-central1, and a lane split across two regions is a lane whose URLs and image paths do not match.

Terraform and the kit's Python sign in through Application Default Credentials, not through gcloud's login. Cloud Shell usually provides them; check, and log in only if the check says so.

bash - Cloud Shell: check ADC, and log in only if it is missing
python - <<'PY'
import warnings; warnings.filterwarnings("ignore", category=UserWarning)
import google.auth
try:
    credentials, _ = google.auth.default()
    print("adc ok:", type(credentials).__name__)
except Exception as e:
    print(f"adc NOT ok ({str(e)[:90]}) - run the two gcloud lines below")
PY
# only if it printed NOT ok:
# gcloud auth application-default login --no-launch-browser
# gcloud auth application-default set-quota-project "$PROJECT"

Phase 2 · Create

Phase 2: APIs, the state bucket and terraform init

Three things Terraform needs before it can plan anything.

A new project has almost every Google API switched off. make apis switches on the 40 the kit uses, in one call, from the kit's own list. It takes a minute or two and bills nothing.

bash - Cloud Shell: enable the kit's APIs
make apis PROJECT="$PROJECT"
gcloud services list --enabled --project="$PROJECT" --format='value(config.name)' | wc -l

Then the state bucket. Terraform will keep its record of the lane here rather than on the Cloud Shell disk, so the record survives a lost session and is versioned, so an accident can be undone. You create this bucket yourself, by hand, because Terraform cannot store its state in a bucket it has not created yet.

bash - Cloud Shell: the state bucket, and Terraform connected to it
gcloud storage buckets create "gs://$TFSTATE_BUCKET" --project="$PROJECT" --location=asia-south1 --uniform-bucket-level-access
gcloud storage buckets update "gs://$TFSTATE_BUCKET" --versioning
terraform -chdir=terraform init -input=false \
  -backend-config="bucket=$TFSTATE_BUCKET" -backend-config="prefix=$TFSTATE_PREFIX"
expected - the last line of terraform initread only
Terraform has been successfully initialized!
Init once, with these values, and never with others

On a lane that already exists, do not run init again with a different bucket or prefix, and never reach for -migrate-state, state rm or an empty backend to get past an error. An empty state on an existing project means Terraform believes nothing exists and would try to create everything twice. Check with terraform -chdir=terraform state list first; the kit's INFRASTRUCTURE.md covers recovery.

Phase 2 · Create

CI trust and Google sign-in, before the plan

Two inputs the plan needs from you, and one console page Terraform cannot fill in.

The kit's Terraform sets up Workload Identity Federation, so that a GitHub Actions workflow can deploy to this project later without a stored key. It needs to know which repository to trust, by name and by its numeric ID. Use a repository you own: a fork of the learner repository, or an empty one made for this. The helper saves your confirmed project, billing and CI inputs, and every later plan is checked against them.

bash - Cloud Shell: save the project and CI inputs
export GH_REPO=YOUR-GITHUB-USER/YOUR-REPO     # a repository you own
export GH_REPO_ID="$(curl -s "https://api.github.com/repos/$GH_REPO" | python -c 'import json,sys; print(json.load(sys.stdin)["id"])')"
echo "trusting $GH_REPO, id $GH_REPO_ID"
python commands/infrastructure.py prepare --project "$PROJECT" --region "$REGION" \
  --github-repository "$GH_REPO" --github-repository-id "$GH_REPO_ID" --deploy-ref refs/heads/main
expectedread only
PASS: saved confirmed inputs to /home/you/deploy_module_rag/terraform/runbook-project.auto.tfvars.json
CI trust: YOUR-GITHUB-USER/YOUR-REPO (ID NUMBER) / refs/heads/main

The saved inputs file stays in your Cloud Shell and is never committed. For a private repository, read the ID with gh api repos/$GH_REPO --jq .id instead of the public API.

Google sign-in for the UI. IAP shows a Google sign-in screen, and that screen needs an OAuth consent screen. Open Google Auth Platform → Branding in the console, set an app name and your support address, and save. Then check whether your project sits inside an organization:

bash - Cloud Shell: organization or not
gcloud projects describe "$PROJECT" --format='value(parent.type,parent.id)'   # empty: no organization

If it printed an organization, IAP manages its own OAuth client and you are done here. If it printed nothing, a personal account with no organization, create the client yourself: Google Auth Platform → Clients → Create client, type Web application, then give its ID and secret to IAP. The file holds a secret, so it lives in your home directory for a moment and is deleted straight after.

bash - Cloud Shell: only without an organization
cat > "$HOME/iap-oauth.yaml" <<'EOF'
accessSettings:
  oauthSettings:
    clientId: CLIENT_ID
    clientSecret: CLIENT_SECRET
EOF
# edit the two values in $HOME/iap-oauth.yaml first (cloudshell edit ~/iap-oauth.yaml)
gcloud iap settings set "$HOME/iap-oauth.yaml" --project="$PROJECT" && rm "$HOME/iap-oauth.yaml"

Phase 2 · Create

make preflight, then make plan: read before you apply

A read-only check of everything the apply stands on, then the one plan you will approve.

make preflight creates nothing. It checks the tools and their versions, your sign-in, the project, the billing link, the state bucket, the APIs and the one Python package the roster needs, and for anything missing it says what to run. Every line should read ok.

bash - Cloud Shell: preflight, read-only
make preflight PROJECT="$PROJECT" TFSTATE_BUCKET="$TFSTATE_BUCKET" REGION="$REGION"
expectedread only
  ok    gcloud on PATH
  ok    terraform on PATH
  ok    make on PATH
  ok    python on PATH
  ok    terraform VERSION (backend.tf wants >= 1.9)
  ok    signed in as you@example.com
  ok    project documind-ai-YOUR-ID exists
  ok    billing linked
  ok    state bucket gs://documind-ai-YOUR-ID-tfstate
  ok    APIs enabled
  ok    google-cloud-firestore for make roster

preflight clean - next: make plan, then make up

Now the plan. make plan runs terraform plan with your saved inputs, writes the plan to a file, and then inspects it the way a reviewer would: it refuses the plan if it is incomplete, if its inputs differ from the ones you confirmed, if it would delete or replace anything, or if it would change an existing CI trust. A plan that passes is recorded as the selected plan, and that file is the only thing make up will apply.

bash - Cloud Shell: the plan, saved and checked
make plan PROJECT="$PROJECT" REGION="$REGION" ADMIN_EMAILS="$ADMIN_EMAILS" 2>&1 | tee "$HOME/plan.log"
grep -E '^(PASS|CI trust|STOP|Plan:)|Reviewed plan|Review the' "$HOME/plan.log"

Look for three things: a Plan: N to add, 0 to change, 0 to destroy line (on a blank project, everything is an add), the PASS: no deletes/replacements line, and your repository on the CI trust line. Then read the plan by resource type, which is far easier than scrolling through Terraform's text:

bash - Cloud Shell: the plan, counted by resource type
PLAN="$(python -c "import json; print(json.load(open('terraform/runbook-selected-plan.json'))['plan'])")"
terraform -chdir=terraform show -json "$PLAN" > "$HOME/plan.json" && echo "saved plan: $(basename "$PLAN")"
python - <<'PY'
import json, os, warnings; warnings.filterwarnings("ignore", category=UserWarning)
from collections import Counter
plan = json.load(open(os.path.expanduser("~/plan.json"), encoding="utf-8"))
changes = [rc for rc in plan["resource_changes"] if rc["mode"] == "managed"]
print("actions:", dict(Counter("/".join(rc["change"]["actions"]) for rc in changes)))
types = Counter(rc["type"] for rc in changes if rc["change"]["actions"] != ["no-op"])
for t, n in sorted(types.items(), key=lambda x: (-x[1], x[0])):
    print(f"{n:4d}  {t}")
print(f"{sum(types.values()):4d}  in all")
PY

The biggest groups are IAM bindings and service accounts, then Firestore indexes, buckets and alert policies. The few that bill by the hour are near the bottom with a count of one or two: the Vector Search index endpoint and its deployed index, the Spanner instance, the two Cloud SQL instances, the GKE cluster and its node pool, and the VPC connector. Step 13 prices each one.

Phase 3 · Deploy

Phase 3: make up applies the plan and deploys everything

One command, 9 stages after the apply, and the longest wait of the day.

Here is the whole of make up, from the kit's Makefile. The first line applies the checked plan; the second runs the deploy stages in order.

deploy/Makefile - the up targetread only
up: guard-project
	$(INFRA) apply $(INFRA_FLAGS) $(INFRA_PLAN)
	$(MAKE) drift secrets build deploy-services wait-index roster managed-stores bq-views vector-status

In order: drift compares the lane with the plan, secrets writes the first versions of the secrets Terraform declared empty, build runs Cloud Build for every image, deploy-services deploys them to Cloud Run, wait-index waits for Firestore's vector indexes to be READY, roster puts you and the UI's account on the tenants, managed-stores creates the RAG Engine corpora, bq-views creates the BigQuery reporting view, and vector-status prints how many vectors the search index holds: zero for now, by design.

The services, and the order they come up in: the ingest worker first, because the upload subscription already points at its URL, then the API, then everything that calls the API. Each one is deployed by its own script under commands/, the same script the lesson that teaches it shows.

deploy/Makefile - what make up builds and deploysread only
SERVICES   = ingest api admin ui chat mcp agent
SCRIPTS    = commands/lesson-12.5.sh commands/lesson-12.2.sh commands/lesson-12.3.sh \
             commands/lesson-12.4.sh commands/lesson-12.8.sh \
             commands/lesson-7.2.sh commands/lesson-8.4.sh

Run it inside tmux. The Terraform apply creates a few hundred resources, some of which (Vector Search, Cloud SQL, Spanner, the GKE cluster) take many minutes on their own, and seven Cloud Build runs follow. Expect well over an hour on a blank project.

bash - Cloud Shell, inside tmux: apply and deploy
time make up PROJECT="$PROJECT" REGION="$REGION" ADMIN_EMAILS="$ADMIN_EMAILS" 2>&1 | tee "$HOME/up.log"
tail -n 25 "$HOME/up.log"

If your connection drops, reattach with tmux attach -t documind; the command kept running. If make up stops during the apply, the plan it applied is used up: fix the cause, then make plan, review, and make up again. Terraform keeps everything the first run created, so the second plan only adds what is missing. If it stops after the apply, in one of the deploy stages, you do not need a new plan at all: step 10 runs only the stages that were left.

When it finishes, count the services and the account each runs as:

bash - Cloud Shell: the services, and who each runs as
gcloud run services list --project "$PROJECT" --region "$REGION" \
  --format='table(metadata.name:label=SERVICE, spec.template.spec.serviceAccountName:label=RUNS_AS)'
gcloud run services list --project "$PROJECT" --region "$REGION" --format='value(metadata.name)' | wc -l

A complete deploy shows 7 rows: documind-ingest, documind-api, documind-admin, documind-ui, documind-chat, documind-mcp, documind-agent, each running as its own documind-<service>-sa account. On today's kit a first make up stops partway through the deploy stage with two of them up; step 10 says why and finishes the job.

The BigQuery view. Why it waits for an answer, in the kit's own words:

deploy/Makefile - bq-views, and why it can stop make upread only
# The SQL that terraform does not own. tenant_daily is a VIEW over the log sink (12.3) and
# was, until 2026-09-05, applied by nobody - the file existed and the view did not.

Phase 3 · Deploy

Seed the lane: operators, the corpus, the vectors

A lane with no documents answers nothing. Three commands fill it.

First, the operator grant. The smoke test and the eval gate call the API as the UI's service account, and the gate's refusal rows call it as an outsider account; both need you to be allowed to mint tokens as those accounts. Project Owner does not include that permission, which is why the kit grants it explicitly.

deploy/Makefile - the operators targetread only
operators: guard-project
	@for who in $$(echo "$(ADMIN_EMAILS)" | tr ',' ' '); do \
	  for sa in documind-ui-sa documind-outsider-sa; do \
	    gcloud iam service-accounts add-iam-policy-binding $$sa@$(PROJECT).iam.gserviceaccount.com \
	      --project=$(PROJECT) --member="user:$$who" --role=roles/iam.serviceAccountTokenCreator \
	      --condition=None --quiet >/dev/null && echo ">> $$who may mint tokens as $$sa"; \
	  done; \
	done
bash - Cloud Shell: let yourself mint tokens as the UI and the outsider
make operators PROJECT="$PROJECT" ADMIN_EMAILS="$ADMIN_EMAILS"

Then the corpus. make ingest-corpus uploads the three tenants' synthetic documents and the real Acts, one folder per tenant, into the uploads bucket. Every object that lands is an event: the ingest worker parses it, chunks it, embeds it and writes it to Firestore and Vector Search. The upload is quick; the indexing behind it takes a while, so make wait-vectors blocks until the search index holds at least 200 vectors, or tells you why not after 20 minutes.

bash - Cloud Shell: load the corpus and wait for the index
make ingest-corpus PROJECT="$PROJECT"
make wait-vectors PROJECT="$PROJECT" REGION="$REGION" WANT=200
make vector-status PROJECT="$PROJECT" REGION="$REGION"

Finally, pin the tenant you will test with to the vector index, so the smoke test checks the tier you expect it to:

bash - Cloud Shell: acme on the vector tier
make tenant-backend PROJECT="$PROJECT" TENANT=acme RETRIEVAL_BACKEND=vector

While you wait, the worker's log is worth watching: each document ends on an ingest_ok line with its chunk count. make dlq peeks at the dead-letter queue without acknowledging anything; an empty queue is what you want.

Phase 3 · Prove it

Prove it: the smoke, the gate and the UI in a browser

Three proofs, from the cheapest to the one you can show someone.

The smoke test. It checks health, asks a golden question as a tenant member and expects an answer with citations, and asks again with no token, which must be refused. It costs one Gemini answer.

bash - Cloud Shell: the smoke test
export API="https://documind-api-$NUMBER.$REGION.run.app"
make smoke DOCUMIND_API_URL="$API" DOCUMIND_PROJECT="$PROJECT" DOCUMIND_TENANT="$TENANT"

If bq-views stopped make up earlier, the API has now answered once, so finish the last two stages:

bash - Cloud Shell: the stages make up could not finish before the first answer

The eval gate. make eval-live runs the whole golden set against the deployed API: answer quality thresholds, the rows that must be answered, the rows that must be refused, and tenant isolation, which must be 100 percent. It makes one Gemini call per row, so it costs more than the smoke; run it once now and again after any change you care about.

bash - Cloud Shell: the golden set against the live API
make eval-live PROJECT="$PROJECT" REGION="$REGION"

make smoke-all runs every smoke the kit has. Two of them, smoke-gateway and smoke-slm, test optional services this page does not deploy, so on this lane expect those two to fail and the rest to pass.

The UI. Print the address and open it in a browser:

Phase 3 · Switch off

What bills by the hour, and how to stop it

Six items bill while they exist, used or idle. Two commands and one deletion stop them.

Cloud Run services cost nothing while they have no instances. These do, every hour, from the moment the apply creates them. Sizes are read from the kit's Terraform; prices are Mumbai list prices read on 7 October 2026, at Rs 85 to the dollar. There are three ways to stop, from gentlest to final.

make off scales the services, the gateway and the GPU services to zero instances. It is what the lane's 23:00 IST job does every night. It does not stop the six items above; they bill until they are deleted.

make down deletes the Cloud Run services first, then runs terraform destroy, and at the end prints what it could not remove: Firestore (delete protection), buckets that still hold objects, the protected managed search stores, and the BigQuery views.

Deleting the project removes everything, including what make down left. Google keeps a deleted project recoverable for 30 days and stops billing it at once.

bash - Cloud Shell: switch off, tear down, delete
make off PROJECT="$PROJECT" REGION="$REGION"       # tonight: services to zero (the hourly items still bill)
make down PROJECT="$PROJECT" REGION="$REGION"      # done for now: services deleted, terraform destroy
gcloud projects delete "$PROJECT"                  # done for good: everything, billing stops

To come back after make down, you do not repeat steps 3 to 7: the kit, the venv, the state bucket and your saved inputs are all still there. Run the session block of step 5, then step 8 and step 9 again. After a project deletion, start again from step 4 with a new project ID.
