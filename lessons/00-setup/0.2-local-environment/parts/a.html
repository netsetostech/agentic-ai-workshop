Level 0 · Theory

What DocuMind is: two workflows on one map

The system this course builds, the two journeys through it, and the box each module opens.

DocuMind is a document-question service for companies, and it is the system every lesson of this course builds, runs and changes. A company, a tenant, uploads its documents: an HR handbook, contracts, an invoice, and the Acts of Parliament it has to comply with. The kit ships %%N_TENANTS%% tenants, acme, zeta and globex. Their employees ask questions in plain words, such as "%%QUESTION%%", and the answer quotes the clause that decides it and names the document and the page it came from. Two promises hold the design together: every answer cites its evidence, and no tenant ever sees another tenant's documents.

Everything DocuMind does is one of two journeys. An upload becomes searchable rows: the file lands in a bucket, an event wakes a worker, and the worker reads the file, cuts it into pieces and writes the pieces to the stores. A question becomes an answer: the UI sends it to the API, the API decides who is asking and for which tenant, the retriever finds the pieces that match, and the generator writes the answer from those pieces alone, citing them. The stores are where the two journeys meet: the worker writes there, the retriever reads there.

🍳

A restaurant kitchen with two doors. Deliveries come in at the back: each crate is checked for whose order it is, cut, labelled with the shelf it goes on, and put away in the cold rooms. That is the upload journey: bucket, worker, stores. Orders come in at the front: the host checks the booking, the cook takes only from that customer's shelves, plates the dish, and the bill names the shelf every item came from. That is the question journey, and the bill is the citation.

Two more rooms belong to this lesson. The test kitchen at home uses the same recipes on a small stove and a home fridge stocked with the same labelled cuts: worse food, no rent. That is the Rs 0 lane, the same chat service on your laptop with a small local model. The inspection before opening checks the kitchen without cooking a meal, and it also checks the inspector's own sheet: a line that says "fridge: cold" with no temperature written down can never fail, so it is refused. That is make dryrun, and the refused line is the failure you will cause in step 6.

The words: clone, venv, lane, profile, golden row

The words this lesson uses, each with the value it has on your machine by the end of it.

WordMeaningOn your machine
CloneA full copy of a Git repository, history included. git pull brings it up to date, git diff shows what you changed, and git checkout undoes it.~/deploy_module_rag, a clone of netsetos/agents_workshop_learner, branch main
KitThe repository's contents: every service, the Terraform, the make targets, the corpus and the evals. The pages quote it line for line.the clone's root, which the pages call $DEMO_ROOT
venvA folder holding one Python interpreter and the packages installed for it, apart from the Python your system uses. source .../bin/activate puts it first on the PATH.~/rag-shell-venv (the operator's, %%N_PINS%% pinned packages) and ~/rag-local-venv (the Rs 0 lane's)
Operator shellThe terminal you run make and the cells from: the kit as the working directory, the operator venv active. Every later lesson opens by restoring it.a prompt that starts with (rag-shell-venv)
LaneYour own deployed DocuMind: the services, stores and accounts of the master diagram, on your Google Cloud project.none yet: lesson 0.3 deploys it
Rs 0 laneThe chat service on your laptop: a local model through Ollama instead of Gemini, a Chroma directory instead of the API and its stores, and no identity checks.127.0.0.1:%%PORT%%, %%LOCAL_MODEL%%, %%N_ACME%% acme chunks
ProfileThe one switch, DOCUMIND_PROFILE, that picks the model and the store. gcp is the default; the agent code is the same either way.local for the Rs 0 lane
Chunk idThe address of one piece of one document. A citation names it, so a reader can open the exact text the answer used.%%TOP_ID%% on the laptop; acme:<sha256>#<position> on the lane
make dryrunThe kit's offline gate, Tier A: three commands, no credentials, no cost. CI runs the same three on every push.validate.py's %%N_CHECKS%% checks, then the eval gate's %%N_EVAL_CHECKS%%
Golden rowOne question with what its answer must contain, which clause it must retrieve, or that it must be refused. The eval gate's unit of judgement.%%N_GOLDEN%% rows; lk-06 is the notice-period row
PASS, WARN, SKIP, FAILA check's verdict. Only FAIL turns the run red. A WARN is printed and passes; a SKIP means the check cannot run here, because its tool is not installed or, for extract, there is nothing to compare.%%N_PASS_VAL%% PASS, %%N_WARN_VAL%% WARN, %%N_SKIP_VAL%% SKIP from validate.py on a machine without Terraform, tflint or Docker

Two of these words carry the rest of the course. The clone is why a kit update is one git pull and a mistake is one git checkout. The profile is why the chat service you run for Rs 0 today is the same code lesson 0.3 deploys and Module 5 takes apart: one switch changes the model and the store, and nothing else.
