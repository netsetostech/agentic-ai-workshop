Practice Lab: Ingest, re-issue, undo, poison

Six drills on the ingest lane, each with the command, the line to watch and the numbers to predict before you run it. Two are Rs 0 and run on the cloned kit alone; four need the live lane from Module 2. By the end you have read every lifecycle line the worker writes, predicted the carry-over counts twice and been right, and left the lane in the state the nightly walk expects.

Before you start

Exercises 2 and 6 are Rs 0: the kit cloned (code/; a clone of the learner repo names the same folder deploy/), Python 3.12, pip install pydantic. Exercises 1, 3, 4 and 5 need a deployed lane from Module 2 with make up done and make smoke green, and in your shell: export PROJECT=documind-ai-YOUR-ID TENANT=acme REGION=us-central1, cd code, google-cloud-firestore and google-cloud-storage installed (the shell that ran make up has them), and the log filter W='resource.type="cloud_run_revision" AND resource.labels.service_name="documind-ingest"' exported. Do the live exercises after lesson 3.5's steps 2 and 3 (the amendment and the corpus are in), and do not ingest evals/demo/smoke_note_v1.md yourself: it is make smoke-reindex's fixture, and the same bytes under any name would make the smoke's first upload a duplicate. Costs: exercises 1, 3, 4 and 5 are under a rupee each; the optional block in exercise 5 parses 236 pages again, about Rs 200 on the default lane.

1 One document in, and the passbook

Easy

Ingest a small synthetic document, read the worker's line field by field, and match every number against the ledger row make sources prints. Done looks like the three numbers on the ingest-one line, the nine fields of the ingest_ok line and the ledger row all agreeing, and you able to say why reused is 0.

  1. Run make ingest-one with evals/corpus/acme/msa_acme_2026.md. Before it prints, write down what chunks will be (the file has a title paragraph above five ## sections).
  2. Read the whole ingest_ok line with gcloud logging read.
  3. Run make sources TENANT_ONLY=acme and find the row.

Complete solution

bash — Cloud Shell
make ingest-one FILE=evals/corpus/acme/msa_acme_2026.md TENANT=acme PROJECT=$PROJECT
gcloud logging read "$W AND jsonPayload.event=\"ingest_ok\" AND jsonPayload.tenant=\"acme\"" \
  --project $PROJECT --freshness=10m --limit 1 --format=json \
  | python -c "import json,sys; print(json.dumps(json.load(sys.stdin)[0]['jsonPayload'], indent=1))"
make sources TENANT_ONLY=acme PROJECT=$PROJECT | grep -E "msa_acme|ledger"
What you should see. If the corpus is already in (lesson 3.5 step 3), the first command prints no ingest_ok in 5 min and exits 1: the same bytes are already documents/acme_<sha> with status indexed, the worker acked the message as ingest_duplicate (a line with only doc_key on it), and nothing was parsed or embedded - which is the first lesson of the exercise. Read that line instead with jsonPayload.event="ingest_duplicate". On a lane without the corpus, the target prints >> indexed: acme_<sha> 6 1 and the line says chunks: 6, pages: 1, kinds: ["text"], reused: 0, embedded: 6, retired: 0, effective_from: null: the preamble (the title and the disclaimer) plus five sections, MSA-01 to MSA-12, and reused is 0 because a first version has no current rows of this source to carry over. The ledger row says indexed, chunks 6, the same generation as the line, and text-embedding-005@1. The cost is 897 characters of embedding: under a paisa.

2 Predict the re-issue offline

Easy

Rs 0. The worker and the notebooks chunk with the same two rules, and shared/documind_corpus.py is importable and pure, so the counts a live make reindex will print can be computed on your laptop before you spend a rupee. Done looks like two predictions - the handbook's re-issue and the smoke fixture's - that lesson 3.5's steps 4 and 8 then confirm.

  1. From the kit root, load acme's documents the notebooks' way and find the handbook.
  2. Chunk revision 1 and revision 2 (evals/demo/hr_policy_2026_v2.md); count the hashes of revision 2 that exist in revision 1.
  3. Do the same for smoke_note_v1.md and smoke_note_v2.md, and name the reused chunk.

Complete solution

python — from the kit root, Rs 0
import sys
sys.path.insert(0, ".")
from shared import documind_corpus as m

docs = m.load_documents("acme", "evals", "documind-ai-YOUR-ID")
hr = next(d for d in docs if d["slug"] == "hr_policy_2026")

def plan(old_text, new_text, name):
    # the carry-over rule of indexer.plan_carry_over: reuse by chunk_hash, embed the rest
    v1 = m.chunk_document(dict(hr, text=old_text), "acme")
    v2 = m.chunk_document(dict(hr, text=new_text), "acme")
    have = {c["chunk_hash"] for c in v1}
    reused = [c["locator"] for c in v2 if c["chunk_hash"] in have]
    changed = [c["locator"] for c in v2 if c["chunk_hash"] not in have]
    print(f"{name}: chunks={len(v2)} reused={len(reused)} embedded={len(changed)} retired={len(v1)} changed={changed}")

read = lambda p: open(p, encoding="utf-8").read()
plan(hr["text"], read("evals/demo/hr_policy_2026_v2.md"), "handbook")
plan(read("evals/demo/smoke_note_v1.md"), read("evals/demo/smoke_note_v2.md"), "smoke")
What you should see. handbook: chunks=283 reused=281 embedded=2 retired=283 changed=['preamble', 'NP-03'] and smoke: chunks=3 reused=1 embedded=2 retired=3 changed=['preamble', 'SM-01']. The handbook's 282 sections plus the preamble are 283 chunks; revision 2 added two lines above the first heading (a new preamble hash) and changed NP-03's 60 to 90, and every other section is byte for byte the same. The smoke fixture's SM-02 is the reused one. These are exactly the numbers make reindex prints in lesson 3.5 step 4 and make smoke-reindex prints in step 8, because main._chunk and chunk_document mint the same texts and hashes - the gate in tools/check_real_corpus.py holds them to it.

3 Re-issue, watch the answer move, undo

Medium

Lesson 3.5's steps 4 and 5 as one drill, with the ledger read between them. Done looks like the two make reindex lines matching exercise 2's prediction, the answer moving from 60 to 90 days and back, and the fingerprint after the undo equal to the fingerprint before the re-issue.

  1. Record acme's fingerprint from make sources.
  2. Re-issue the handbook as revision 2; read the line and the ingest_superseded line; ask the API the notice-period question.
  3. Upload revision 1 again; read the line; ask again; compare the fingerprint.

Complete solution

make sources TENANT_ONLY=acme PROJECT=$PROJECT | tail -1

TOKEN=$(gcloud auth print-identity-token --include-email --impersonate-service-account=documind-ui-sa@$PROJECT.iam.gserviceaccount.com --audiences=$API)

  -d "{\"query\":\"$1\",\"tenant_id\":\"acme\",\"user_id\":\"u_lab\",\"top_k\":5,\"stream\":false}" | python -c "import json,sys; print(json.load(sys.stdin).get('answer'))"; }

What you should see. First line: ingest_ok acme_<rev2> 283 281 2 283 2026-10-01, then retired (doc_keys, chunks, expire days): acme_<rev1> 283 30. The answer says 90 days and, because revision 2 declares a date, effective from 2026-10-01. Second line: ingest_reactivated acme_<rev1> 283 283 0 283 with no retired line under it - the undo logs no ingest_superseded. The answer says 60 days. The two make sources tails print the same fingerprint and versions: 22 (23 if exercise 1 added the MSA on a lane without the corpus), because corpus_fingerprint hashes the set of current doc_keys and the same set is current again. Cost: two chunks embedded on the way out, nothing on the way back, two Gemini answers - under a rupee.

4 The tombstone against every path

Medium

A withdrawn source must survive three things that would bring a merely retired one back: the same bytes uploaded again, a redelivery, and the nightly walk. Prove all three on the amendment, then bring it back the one way that works. Done looks like the ingest_withdrawn line, the plan's withdrawn, object kept line with drift: 0, a refused make restore on a source that is not withdrawn, and the ingest_reactivated line after the real restore.

  1. make retire the amendment; check the ledger row's status.
  2. Upload the same bytes; read the worker's line. Run the plan.
  3. Try make restore on acme/msa_acme_2026.md (not withdrawn) and read the refusal; then restore the amendment and read the worker's line.

Complete solution

bash — Cloud Shell
make retire SOURCE=acme/gratuity_amendment_2026.md PROJECT=$PROJECT
make sources TENANT_ONLY=acme PROJECT=$PROJECT | grep gratuity
gcloud storage cp evals/demo/gratuity_amendment_2026.md gs://$PROJECT-uploads/acme/ --project $PROJECT
sleep 30; gcloud logging read "$W AND jsonPayload.event=\"ingest_withdrawn\"" --project $PROJECT --freshness=5m --limit 1 --format='value(jsonPayload)'
make reconcile TENANT_ONLY=acme PROJECT=$PROJECT
make restore SOURCE=acme/msa_acme_2026.md PROJECT=$PROJECT; echo "exit $?"
make restore SOURCE=acme/gratuity_amendment_2026.md PROJECT=$PROJECT
sleep 30; gcloud logging read "$W AND jsonPayload.event=\"ingest_reactivated\"" --project $PROJECT --freshness=5m --limit 1 \
  --format='value(jsonPayload.doc_key,jsonPayload.chunks,jsonPayload.embedded,jsonPayload.retired)'
What you should see. reconcile_withdrawn with retired_chunks: 3 and a new fingerprint; the ledger row withdrawn. The worker's line for the re-upload is ingest_withdrawn with hint: make restore SOURCE= clears the tombstone - it downloaded the bytes, lost the claim, asked withdrawn() before reactivate(), and acked. The plan prints {"reconcile": "withdrawn", ..., "why": "withdrawn, object kept (generation A -> B: make restore re-ingests what the object holds now)"} and ends "withdrawn": 1, "drift": 0: a decision is not drift. The first restore prints reconcile_restore_refused with only a withdrawn source is restored and exits 1. The second prints reconcile_restored with the new generation, and thirty seconds later the worker says ingest_reactivated - chunks 3, embedded 0, retired 0 - because the ledger row went to retired first and the rewrite took the worker's ordinary undo path. Rs 0.

5 Poison, the DLQ, and the object that drifts every night

Challenge

Break the lane on purpose, read what Pub/Sub did with it an hour later, and find the trap the zero-byte object sets for the nightly walk. Done looks like the ingest_poison error text naming the field, the DLQ row, a reconcile plan that says reingest for the poison object with drift: 1, and a clean plan after you fix it the only right way.

  1. make poison; write down which field of IngestMessage refused it and why the worker answered 400 rather than 500.
  2. Run the reconcile plan while the object is still in the bucket.
  3. Fix it; run the plan again. About an hour after step 1, make dlq, then drain it.
  4. Optional, about Rs 200: step 7's batch-lane block from lesson 3.5, with make reconcile run while the document is queued.

Complete solution

bash — Cloud Shell
make poison PROJECT=$PROJECT
make reconcile TENANT_ONLY=acme PROJECT=$PROJECT
gcloud storage rm gs://$PROJECT-uploads/acme/poison-*.pdf --project $PROJECT
make reconcile TENANT_ONLY=acme PROJECT=$PROJECT | tail -1
# about an hour later
make dlq PROJECT=$PROJECT
gcloud pubsub subscriptions pull ingest-dlq-sub --project $PROJECT --auto-ack --limit=10
What you should see. make poison prints the worker's refusal within two minutes: 1 validation error for IngestMessage / size / Input should be greater than or equal to 1 - contracts.IngestMessage declares size: int = Field(ge=1), and Cloud Storage's record for an empty object says "0". The worker answers 400 because the message would fail identically on every retry; a 500 would buy twelve retries of a certainty. The plan prints {"reconcile": "reingest", "name": "acme/poison-<epoch>.pdf", "why": "not in the ledger"} and "drift": 1: the object is in the bucket, its sha is not a version, so the walk would rewrite it every night and the worker would refuse it every night. After gcloud storage rm, drift: 0. make dlq shows one row (message id, acme/poison-<epoch>.pdf, the event time, delivery attempt 1 of the dead-letter subscription) only once twelve deliveries have failed - the Makefile's few minutes predates eventarc.tf's twelve attempts, so expect about an hour. For the optional block, the plan while the Act is queued prints {"reconcile": "queued", ..., "why": "handed to the batch lane; the batch job indexes it, the claim says queued"} and "queued": 1, "drift": 0.

6 Price the corpus load before you run it

Challenge

Rs 0. Every rupee in lesson 3.5's cost table comes from two counts the kit already holds - Document AI pages in evals/real_sources.json, characters from the chunker - and three rates. Recompute the table for both residencies, then for a corpus of your own. Done looks like a table per tenant (pages, characters, Rs on Layout Parser, Rs on OCR, Rs of embeddings) whose totals match the lesson's 1,065 pages, 3.47 million characters, about Rs 905 / Rs 136 / Rs 7.

  1. Sum pages per tenant from real_sources.json (the tenants list says who holds each Act).
  2. Chunk every tenant's documents with chunk_document and sum the characters.
  3. Price them at $10 and $1.50 per 1,000 pages and $0.000025 per 1,000 characters, at USD_INR = 85.

Complete solution

python — from the kit root, Rs 0
import json, sys
sys.path.insert(0, ".")
from shared import documind_corpus as m

USD_INR = 85
LAYOUT, OCR, EMBED = 10 / 1000, 1.5 / 1000, 0.000025 / 1000   # $ per page, per page, per character - re-verify on the pricing pages
real = json.load(open("evals/real_sources.json", encoding="utf-8"))
pages = {t: 0 for t in ("acme", "zeta", "globex")}
for r in real:
    for t in r["tenants"]:
        pages[t] += r["pages"]
total_p = total_c = 0
for t in pages:
    chars = sum(len(c["text"]) for d in m.load_documents(t, "evals", "documind-ai-YOUR-ID")
                for c in m.chunk_document(d, t))
    total_p += pages[t]; total_c += chars
    print(f"{t:7} pages={pages[t]:5} chars={chars:9,} layout=Rs {pages[t]*LAYOUT*USD_INR:6.0f} ocr=Rs {pages[t]*OCR*USD_INR:5.0f} embed=Rs {chars*EMBED*USD_INR:4.1f}")
print(f"all     pages={total_p:5} chars={total_c:9,} layout=Rs {total_p*LAYOUT*USD_INR:6.0f} ocr=Rs {total_p*OCR*USD_INR:5.0f} embed=Rs {total_c*EMBED*USD_INR:4.1f}")
What you should see. acme pages=685 chars=2,064,459 layout=Rs 582 ocr=Rs 87 embed=Rs 4.4, zeta pages=325 ... layout=Rs 276 ocr=Rs 41 embed=Rs 2.6, globex pages=55 ... layout=Rs 47 ocr=Rs 7 embed=Rs 0.4, and all pages=1065 chars=3,471,913 layout=Rs 905 ocr=Rs 136 embed=Rs 7.4. The characters are the mirrors' - the POSH scan has no mirror and the three figures are captions written at ingest, so the worker's real character count is a little higher - and Document AI is more than ninety per cent of the bill on either processor. The rates are the only inputs not in the code; the page says where they were read and when.
