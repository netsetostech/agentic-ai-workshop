Interview Q&A: Ingest, re-issue, undo, poison

Ten questions an interviewer asks someone who claims to have operated a document pipeline in production, answered the way a senior engineer answers: the mechanism, the failure it prevents, the number, and what you would say if pushed.

Interviewers probing this topic are not testing whether you know what a Pub/Sub dead-letter topic is. They are testing whether you have run a lifecycle and read its lines: what you look at when a re-issue prints the wrong counts, what a 400 buys you that a 500 does not, why a job that repairs storage must never repair a person's decision, and what an operation costs before you run it. The best answers name a log line, a number and the file the number comes from. DocuMind's numbers are used below because they are real; substitute your own system's when you have them.

Conceptual · Q1

What does "an update costs what changed" mean operationally, and what line proves it?

It means the pipeline identifies content at three grains and only pays at the finest one. A source is an object path; a version is the sha256 of the bytes; a chunk is the sha256 of its whitespace-collapsed text plus a locator that survives an edit above it. When a document is re-issued under the same name, the worker matches every new chunk against the current rows of that source by chunk_hash and by the embedding stamp (model, version, task type), copies the vector on a hit and embeds only the misses. The proof is one log line: ingest_ok with reused, embedded and retired. For a 283-chunk handbook with one clause changed, DocuMind's line reads reused=281 embedded=2 retired=283 - the preamble and the changed clause were embedded, 281 vectors were copied, and the old version's 283 rows were flagged.

If pushed on why the number matters when two embeddings cost less than a paisa: because the same rule is what makes a chunker choice a business decision. Fixed windows over the whole document reused none of 92 windows after one inserted line; chunking by section reused 281 of 283. And because a Terraform variable, EMBEDDING_VERSION, is stamped on every row, an embedding-model upgrade reuses nothing - visibly and on purpose.

Conceptual · Q2

A worker behind a push subscription can answer 200, 400 or 500. What does each tell Pub/Sub, and how do you choose?

A 200 acknowledges: the message is done and will never be delivered again. A non-2xx nacks: Pub/Sub redelivers with backoff until the subscription's max_delivery_attempts is exhausted, then forwards the message to the dead-letter topic. The choice is about whether a retry can change the outcome. A message the worker can never parse - a zero-byte object, a record with no tenant prefix - fails identically every time, so DocuMind answers 400, logs ingest_poison with the validation error, and lets the retry ceiling carry it to the DLQ where a person reads it. A transient failure - Document AI unavailable, a Firestore timeout - answers 500 after releasing the claim, so the retry can take the claim and succeed. And a duplicate, a stale generation, a queued document or a withdrawn source answers 200, because those are successes: retrying them would achieve nothing and would hide the fact in a retry loop.

The number to know is the ceiling and why it is what it is. DocuMind's subscription allows twelve attempts with backoff from 10 s to 600 s, not five, because a corpus upload lands thirty objects at once, the worker takes one request per instance, and Cloud Run's cold-start refusals count as attempts; five attempts sent a healthy document to the DLQ on the first live load. The consequence you must be able to state: a poisoned message takes about an hour to appear in make dlq.

Conceptual · Q3

Why is a document withdrawn by a person a different state from a document deleted from the bucket, and why does the nightly job treat them differently?

Because one is storage absence and the other is a decision, and a job may repair the first but never the second. When an object leaves the bucket nothing fires - deletions have no trigger - so the nightly reconcile is the only thing that notices; it retires the rows (a flag with a 30-day expiry, never a delete) and writes retired on the ledger row. If the object comes back, the walk plans a re-ingest and the worker's own undo path reactivates the rows: the system healed itself, which is right, because the object's absence was the whole reason. A person running make retire leaves the object in place on purpose. If that row also said retired, the next night's walk would read "retired but back in the bucket" and resurrect what the person took down - which is exactly what DocuMind's first planner did on 12 September 2026. So the row says withdrawn, the plan reports withdrawn, object kept and does nothing, the same bytes uploaded again are acked as ingest_withdrawn, the undo refuses (reactivate_withdrawn), and only make restore clears it. If pushed: this is the same principle as the DPDP Act's distinction between data you lost and data you were told to stop using - the second must not come back because a backup was restored.

Practical · Q4

A re-issue you expected to print reused=281 embedded=2 printed reused=0 embedded=283. Walk me through what you check.

In order of likelihood. First, the object name: the carry-over reads the current rows of this source, so a file uploaded as hr_policy_2026_v2.md instead of under the old name is a new source with nothing to reuse - make reindex NAME= exists for exactly this. Second, the embedding stamp: held_vectors rejects a row whose embedding_model, embedding_version or embedding_task_type differs from the worker's, so a worker redeployed with a new EMBEDDING_VERSION, or rows written before the RETRIEVAL_DOCUMENT stamp existed, reuse nothing by design; make sources shows the stamp per row. Third, the chunker: if the document lost its ## headings, it fell from section chunking to fixed windows, every window moved, and every hash changed - chunks on the line would also have changed from 283 to about 92. Fourth, the text itself: a mirror re-fetched with a different provenance header, or a PDF re-parsed by a different Document AI processor after a RESIDENCY change, produces different chunk texts. The check that settles it in a minute is offline and free: chunk both versions with shared/documind_corpus.chunk_document and count the shared hashes, which is what the module's practice lab does before spending a rupee.

Practical · Q5

Ten minutes after a poison upload the DLQ is empty. What do you check, and when do you stop worrying?

First the worker's line: gcloud logging read for ingest_poison with the error text - if it is there, the worker did its part and the question is only Pub/Sub's timing. Then the subscription: gcloud pubsub subscriptions describe documind-ingest-push must show a dead-letter policy naming the DLQ topic and the attempt ceiling, and the project's Pub/Sub service agent must hold pubsub.publisher on the DLQ topic and pubsub.subscriber on the push subscription - two grants that fail silently when missing, both declared in eventarc.tf. Then the arithmetic: twelve attempts with exponential backoff from 10 s capped at 600 s is roughly 10 + 20 + 40 + 80 + 160 + 320 + five times 600 seconds, about an hour, so at ten minutes the message is on its fourth or fifth delivery and nothing is wrong. I stop worrying when the line is there and the policy is there; I start again if the row has not appeared ninety minutes after the line. And I read the row with a pull that does not ack, so the next person sees it too, then drain with --auto-ack once it is understood. The stale comment I would fix while I am there is the Makefile's make dlq in a few minutes, written when the ceiling was five.

Practical · Q6

The nightly reconcile reports drift 1 every night, and the alert fired after the second night. How do you find the object?

The job prints one line per action before reconcile_done, so I read its log under resource.type="cloud_run_job" for documind-reconcile and look for the action lines: {"reconcile": "reingest", "name": ..., "why": "not in the ledger"} or "retire" or "backfill". A reingest that repeats nightly for the same name is the signature of an object the worker cannot index: the walk rewrites it onto itself, the worker refuses or fails it, and tomorrow it is still not in the ledger. The commonest cause on DocuMind is a zero-byte object left behind by make poison, which the worker answers 400 to every night and which fills the DLQ each time; the fix is to delete the object, because nothing on the lane deletes and the walk cannot repair a file that can never be parsed. The other cause is a document that throws - ingest_failed in the worker's log with the error, and documents/{doc_key}.error carrying the same text; that is fixed by fixing the cause and re-uploading, since the next delivery may retake a failed claim. If pushed on why the policy waits two nights: one night's drift is a lost event the walk just repaired; drift that survives a run is a lane nobody is reconciling.

Practical · Q7

You must re-issue a 400-page contract. What happens on the push path, and how do you follow it to the end?

The push handler counts the PDF's pages off its page tree with pypdf before any OCR is paid for; over MAX_INLINE_PAGES (250) it writes ingest_batch/{doc_key} with the object, generation and type, sets the claim to queued, logs ingest_queued_batch with a consumer field, starts the batch job if the worker knows its name, and acks. The consumer is a Cloud Run job on the same image with a 7,200 s timeout that takes each queued claim in a transaction, fetches the bytes by generation and runs the same index_document() with lane=batch; an hourly schedule backstops the start. To follow it: make queued lists the queue; the ingest_ok line comes from the job's log, not the service's, so make reindex - which polls the service's log - reports no ingest line in 5 min and exits 1 while the document is being indexed correctly; read resource.labels.job_name="documind-ingest-batch" for batch_run and the line with lane=batch. Two honest details if pushed: the same bytes as an indexed version never reach the page count at all (they lose the claim and are acked as a duplicate), and the ceiling is a constant in main.py, so changing it is an image build and a deploy, not an environment flag.

System design · Q8

Design the undo window for a customer who wants ninety-day reversibility and DPDP erasure on request. Where do the two pull against each other?

Reversibility is a retention number and a state machine. The number is one Terraform variable, retention_days, read by the worker (which stamps expire_at on every retired row), by the TTL policy on chunks.expire_at (the only deleter on the lane), by reactivate() (which refuses an undo older than the window) and by the reconcile; setting it to 90 changes all four at once, and the audit bucket's own five-year retention lock is separate. The undo is verified: the rows still on disk are counted against the claim's chunk count and the retire stamp against the window, so a partial undo is refused and the bytes are ingested fresh rather than leaving a source with no current version. Erasure pulls the other way: "retire, never delete" keeps a withdrawn document's text on disk for the whole window, and a data-principal's request under the DPDP Act may not wait ninety days. The design answer is to keep the two on different fields: make retire for a business withdrawal (the tombstone, the window, the free undo), and for a legal erasure a documented path that sets expire_at to now on the withdrawn rows so the same policy removes them within a day - make purge APPLY=1 is the manual twin - plus the managed-store mirror's delete (which the policy never refuses, because it is the direction the policy wants) and an audit event recording who asked. What I would not do is add a delete call to the worker: the whole guarantee rests on a single declared deleter.

System design · Q9

A Mumbai customer will load 5,000 documents a night with residency in India. Size the lane and name what changes from the course's deployment.

Start from what the lane already does under load: a push subscription with an OIDC token, a worker at concurrency 1 scaling to 30, a 600 s request ceiling matching the ack deadline, twelve delivery attempts because cold-start refusals count, a DLQ, and a batch job for anything over 250 pages. Residency changes two things: RESIDENCY=india selects the Enterprise OCR processor in asia-south1 (the Layout Parser runs only in us), and the tenant's data_region is set to in so the managed mirror never copies text out (mirror_policy_skipped); the Firestore rows, the uploads bucket and the audit bucket are already in the India region. The bill is per page: OCR at $1.50 per 1,000 pages, so 5,000 documents at 40 pages is 200,000 pages, $300, about Rs 25,500 a night, against embeddings in the low hundreds of rupees - the parser is the cost line, so I would keep the pypdf page count before OCR and the batch hand-off exactly as they are. Throughput: at roughly a second a page and one document per instance, 30 instances clear a 40-page document every 40 s, about 2,700 documents an hour; a 5,000-document night fits in two hours inline, and the remainder queues rather than fails. What I would change: raise --max-instances against the Document AI quota rather than against Cloud Run, keep the 12-attempt ceiling, and schedule the reconcile after the load window, not before it, so the night's drift measures the load. What I would not change is the tenant prefix as the isolation key.

Trade-off · Q10

Carry-over by chunk hash means an embedding-model upgrade reuses nothing. Is the stamp worth it, and how would you ship the upgrade?

It is worth it, because the alternative is silent corruption. A vector made by text-embedding-005 with the RETRIEVAL_DOCUMENT task is not comparable to one made by a different model or task, and DocuMind learned this the hard way: rows embedded without a task type defaulted to the query task, retrieval quietly degraded while every count looked healthy, and the repair (reconcile.py --backfill-vectors) had to find them by the missing stamp. So the stamp - model, version, task type, 768 dimensions - is checked on every reuse, and an upgrade that flips EMBEDDING_VERSION reuses zero vectors by design; the cost of that honesty is one full re-embed, which for DocuMind's 2,757 chunks is about Rs 7, and even for a corpus a thousand times larger is a few thousand rupees against Document AI's pages, which an embedding upgrade never has to pay again because the text is already parsed. How to ship it: not in place. Embed the new version into a second index behind a candidate revision, run the scoped live gate and the ablation against the old one, promote by name, and let the old rows retire through the same 30-day window as any other version - the re-embed target the kit's own roadmap (INDEXING.md, section 8) lists and has not built yet. If pushed on the trade-off in one line: pay a known rupee amount once, or pay in answers you cannot see going wrong.

How to prepare

Run lesson 3.5's eight drills on your own lane once, and keep the log lines - an answer with reused=281 embedded=2 retired=283 in it is worth ten with "it reuses embeddings".
Know the five numbers cold: 250 pages, 12 attempts, 30 days, 400 writes a batch, 768 dimensions - and the file each one lives in.
Have one story of a thing that went wrong (the resurrected withdrawal, the five-attempt DLQ, the missing task type) and what line found it.
