Live Session: Ingest, re-issue, undo, poison

Ninety minutes of the lifecycle run live on the instructor's lane, with the room predicting every number before the command runs. The corpus goes in before the session, the poison goes in an hour before, and the session ends on make smoke-reindex green and the one sentence the module asks for.

Session goal

Every learner leaves able to run the eight drills of lesson 3.5 on their own lane and to read each line the worker writes without a page in front of them. They have predicted reused=281 embedded=2 retired=283 and seen it, seen the undo embed nothing and the fingerprint return to its old value, and watched a tombstone hold against the same bytes and the nightly walk. They can say, unprompted, why the undo cost nothing.

Prep checklist

Before the room fills
  • A lane from Module 2 with make up done and make smoke green; PROJECT, TENANT=acme, REGION exported; cd code; the shell that ran make up (it has google-cloud-firestore and google-cloud-storage).
  • Thirty minutes before: make ingest-corpus, then make wait-vectors WANT=200. Do not ingest the amendment or the smoke fixture yet.
  • Sixty minutes before: make poison, so make dlq has a row to show at minute 60. Leave the zero-byte object in the bucket on purpose (minute 70 uses it).
  • Tabs open: Cloud Shell with the lesson's W filter exported; a second Cloud Shell tab running gcloud beta run services logs tail documind-ingest --region $REGION --project $PROJECT; the Firestore console on sources; lesson 3.5's step 1 table of lines on a screen the room can read.
  • A saved query in Logs Explorer: resource.labels.service_name="documind-ingest" AND jsonPayload.event=~"^ingest_".
  • The ask shell function from lesson 3.5 step 4 defined, and one answer already fetched so the API is warm.

Minute 0-5: the passbook and the POD

Open with the log, not with slides. Thirty-one lines are already there from the prep; show them and make the point that the session will never claim a document is indexed - it will read the line that says so, the way a courier's proof of delivery is read and a passbook is read.

bash - Cloud Shell
gcloud logging read "$W AND jsonPayload.event=\"ingest_ok\"" --project $PROJECT --freshness=2h --limit 50 \
  --format='value(jsonPayload.tenant,jsonPayload.pages,jsonPayload.chunks,jsonPayload.reused,jsonPayload.embedded)' | sort | head -40

Point at the reused column: every line says 0. Ask the room why, before you tell them: a first version has no current rows of its source to carry over. Then ask what the handbook's line says under chunks - 283 - and tell them that number will come back three times today.

Minute 5-15: drill 1, one document in

bash - Cloud Shell
head -6 evals/demo/gratuity_amendment_2026.md
make ingest-one FILE=evals/demo/gratuity_amendment_2026.md TENANT=acme PROJECT=$PROJECT
gcloud logging read "$W AND jsonPayload.event=\"ingest_ok\" AND jsonPayload.tenant=\"acme\"" --project $PROJECT --freshness=5m --limit 1 --format='value(jsonPayload)'
make sources TENANT_ONLY=acme PROJECT=$PROJECT | grep -E "gratuity|ledger"

Show the file's first six lines first and take predictions: how many chunks (three: the preamble and two sections whose headings have no clause code), what effective_from will be (2026-10-01, from the document's own line, not from anyone typing it). Run it. The line to point at is "reused": 0, "embedded": 3, then the ledger row's effective column. Question for the room: if a second person uploads this same file as gratuity_v2.md tomorrow, what line does the worker write? (ingest_duplicate: a version is the hash, not the name.)

Minute 15-25: drill 2, the corpus's bill

bash - Cloud Shell
make vector-status PROJECT=$PROJECT
gcloud logging read "$W AND jsonPayload.event=\"ingest_ok\" AND jsonPayload.pages>100" --project $PROJECT --freshness=2h --limit 5 \
  --format='value(jsonPayload.tenant,jsonPayload.pages,jsonPayload.chunks,jsonPayload.doc_key)'

The line to point at is vectorsCount - the ANN tier's own number, a few minutes behind the rows - and the CGST Act's 236 pages. Put lesson 3.5's cost table up and have the room do one row: 1,065 pages at $10 per 1,000 is $10.65, Rs 905 at 85; at Mumbai's OCR rate $1.60, Rs 136. Then the embeddings for 2,757 chunks: Rs 7. Ask: where does the money go on a re-issue of a PDF? (Document AI parses every page again; the carry-over saves embeddings only.) Say plainly that the rates are from the pricing pages, not the code, and dated.

Run the diff first: two lines added above the first heading, 60 changed to 90 in NP-03. Take predictions for reused, embedded, retired and write the room's numbers on the board before Enter. The line: ingest_ok ... 283 281 2 283 2026-10-01, then the retired line with revision 1's key and 30. Point at the 2 and ask which two (the preamble and NP-03). Then the scoped gate, and let it go red; the question for the room is whether that is a bug (no: vr-01 and lk-06 did not move with the document, and in a real release they move in the same commit).

Minute 50-60: drill 5, retire and restore

Prediction first: the same bytes after a retire - reactivated or refused? The line is ingest_withdrawn with its hint. Then the plan: withdrawn, object kept, drift: 0. Ask why the plan does not count it (a decision, not storage absence) and tell the 12 September story: the row used to say retired, and the walk resurrected what a person had taken down. After make restore, show the worker's ingest_reactivated in the tail tab.

Minute 60-70: drill 6, poison and the DLQ

bash - Cloud Shell
gcloud logging read "$W AND jsonPayload.event=\"ingest_poison\"" --project $PROJECT --freshness=2h --limit 1 --format='value(jsonPayload.error)'
make dlq PROJECT=$PROJECT
grep -n -B3 max_delivery_attempts terraform/eventarc.tf

The error text names the field - size, greater than or equal to 1 - and the room should be able to say why that is a 400 (it would fail identically every time) and what a 500 would have bought (twelve retries). Then the DLQ row from the poison you ran an hour ago, and the grep: twelve attempts, and the comment above it explaining why twelve and not five (cold-start refusals on a corpus upload count as attempts). Say that the Makefile's own few minutes is stale and the subscription is what runs.

Minute 70-80: drill 7, reconcile and drift

bash - Cloud Shell
make reconcile TENANT_ONLY=acme PROJECT=$PROJECT
gcloud storage rm gs://$PROJECT-uploads/acme/poison-*.pdf --project $PROJECT
gcloud storage rm gs://$PROJECT-uploads/acme/gratuity_amendment_2026.md --project $PROJECT

make reindex FILE=evals/demo/gratuity_amendment_2026.md TENANT=acme PROJECT=$PROJECT

Three plans, three predictions. First: the poison object is reingest, drift 1 - ask what APPLY=1 would do to it every night (rewrite it, poison again, DLQ again) and why deleting it is the only fix. Second, after the amendment is deleted: retire, drift 1, and with APPLY=1 the reconcile_retired line and the ledger row retired. Third, after the object is back through make reindex (which matches the ingest_reactivated line): drift 0. Close the segment with the two drifts that share a word: make drift is Terraform's, this field is the ledger's.

Minute 80-88: the gate

bash - Cloud Shell
make smoke-reindex PROJECT=$PROJECT

Take one prediction while it runs: which of the fixture's three chunks will be reused (SM-02). Read the seven PASS lines aloud as they come - the whole session again on three chunks in two minutes. Then two minutes on the batch lane with lesson 3.5's step 7 on the screen: the corpus has no file over 250 pages, the same bytes would be a duplicate, and what it takes to see the lane. Minute 88-90: close

Ask for the sentence one more time - why did the undo embed nothing - and run make off PROJECT=$PROJECT on screen so the floors go to zero before anyone leaves. Assign the homework.

If it breaks

make ingest-one prints "no ingest_ok in 5 min"

Read gcloud logging read "$W AND jsonPayload.event=\"ingest_failed\"" --freshness=10m first: the error field is the diagnosis. If there is no line at all, the push never arrived: gcloud pubsub subscriptions describe documind-ingest-push --project $PROJECT must show the worker's URL and documind-ingest-sa as the OIDC account, and make dlq may already hold the message. If the line is ingest_duplicate or ingest_withdrawn, nothing broke - the target only waits for ingest_ok; say so and move on.

make reindex stops before uploading: "the golden set is not sound"

The offline gate ran first and was red: someone edited evals/golden.jsonl or evals/corpus/ on this checkout. Run python evals/run_eval.py and read the first failing check; a reindex is a release and the target refuses on purpose. For the session, git stash the change and re-run; do not bypass the gate.

make smoke-reindex fails its first check: "no worker line in time"

Version 1 of the fixture was already current on this lane - a previous run, or someone ingested smoke_note_v1.md by hand - so the worker acked it as ingest_duplicate, a line the smoke's tenant filter cannot see. Recover in three commands: gcloud storage rm gs://$PROJECT-uploads/acme/smoke_note.md, make reconcile APPLY=1 (the walk retires it), make smoke-reindex again - the first check now reads ingest_reactivated.

Discussion prompts

  1. The carry-over saved thirty-four paise on the handbook. Why does the course still call it the most important number in Module 3?
  2. Deleting an object and running make retire both flag the same rows for thirty days. Name every way the two states behave differently afterwards.
  3. Twelve delivery attempts with backoff to 600 s means a poisoned message takes about an hour to reach the DLQ. What would you change for a customer who wants poison visible in five minutes, and what would it cost you on a corpus upload?
  4. make usage prices answers, not ingests. Where would you put the ingest's rupees so that tenant_daily could show them next to the answers?
  5. The smoke runs once per lane because of a filter on a field one line does not carry. Is the fix in the worker, the smoke, or the filter - and who should own it?
