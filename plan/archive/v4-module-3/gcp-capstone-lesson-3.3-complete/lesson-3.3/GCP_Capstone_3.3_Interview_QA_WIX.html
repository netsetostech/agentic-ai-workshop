Interview Q&A: from bytes to rows

Ten questions an interviewer asks about the write path of a document index - the contract at the edge, parsing under a page limit, scanning for personal data without storing it, chunk identity, embedding limits and the carry-over, writing to stores that share no transaction - answered the way a senior engineer answers them: the mechanism, the failure it prevents, the number, and what you say when pushed.

Interviewers who probe this topic are not testing whether you know what an embedding is. They are testing whether you have shipped an ingest path that survived a duplicate upload, a quota refusal, a residency clause and a re-issued document - and whether you can say which line handled each. The DocuMind kit gives you concrete answers: a content-hash version key, a 15-page slice, a 400,000-byte scan request, a whitespace-collapsed chunk hash, a 250-text batch, four restricts. Use the numbers. An answer with a number in it sounds like experience because it is.

Conceptual · Q1

Why is a document's version key a hash of its content, scoped to the tenant, and not the Pub/Sub message id?

Because the two duplicates you actually meet are different. A redelivery keeps its message id, so the id would catch a retry. But the same PDF uploaded twice - by two colleagues, or by one person unsure the first upload worked - is two messages with two ids, and that is the duplicate users create. A content hash catches both: same bytes, same key, the second delivery loses the claim, nothing is parsed or embedded twice.

The tenant scoping comes from a real failure. Until 7 September 2026 the chunk id was sha256#i; the corpus shares seven Acts between tenants, so the second tenant to ingest an Act overwrote the first tenant's rows with its own tenant_id, and the live eval refused eight questions about documents ACME had uploaded. doc_key = tenant_sha256 and chunk_id = tenant:sha256#i make the same bytes under two tenants two documents. If pushed on cost - "you store the Act twice" - say yes, and that storage is cheaper than one cross-tenant answer.

Conceptual · Q2

Why chunk a handbook by section rather than by fixed windows, when fixed windows are simpler?

Because identity across versions is worth more than simplicity. A fixed window is positional: insert one line at the top and every window after it shifts, so every window's text changes. DocuMind measured it on its own handbook - a re-issue that changed one clause reused none of its 92 windows. A section is content-addressed: the clause code in the heading is the locator, the section's text is the hash, and an edit above a section moves neither. The same re-issue reuses 281 of 283 sections and embeds two.

The mechanism is two regular expressions and one rule: a line starting with ## opens a section; a heading that starts with a code like NP-03 lends it as the locator, otherwise the ordinal does; a section over 2,000 characters is windowed within itself. Documents without headings - an Act's PDF - still get fixed windows, cut page by page so a chunk never straddles a page and can be cited by page. The trade-off to admit: section sizes vary. In a policy corpus that is right, because the section is the unit a question is answered from.

Conceptual · Q3

Why does a stored vector carry the embedding model, version and task type, and why is a vector without the task type never reused?

A vector is only meaningful against vectors made the same way. Reusing one from a previous version saves money only if a query embedded today lands in the same space, so the stamp records what made the vector: the model, a version you bump when anything upstream changes, and the task type. The carry-over reuses a vector only when all three match and the vector is finite and 768-dimensional.

The task type is the one people forget, and DocuMind learned it on 17 September 2026. The worker used to omit it; the text-embedding API's default for an omitted task is RETRIEVAL_QUERY, while documents must be encoded as RETRIEVAL_DOCUMENT and questions as RETRIEVAL_QUERY - the asymmetric pair the model is trained for. Rows without the stamp had been encoded as if they were questions. Reusing them would carry a quiet retrieval defect forward for ever, so document_embedding_matches refuses them, the carry-over embeds the chunk fresh, and a repair job re-embeds and stamps the old rows in bulk. If pushed - "over-engineering?" - say the stamp costs three string fields a row, and the alternative was a corpus where you could not tell which vectors were wrong.

Practical · Q4

A 236-page Act arrives. How do you parse it with Document AI inside one request, and when is a document too big for the request path?

Two numbers. Document AI's online request takes at most 15 pages, for OCR and the Layout Parser alike, so the worker opens the PDF with pypdf and, past 15 pages, writes 15-page slices with PdfWriter and sends them one after another; the pages come back in order and are joined with a form feed so the chunker can cut on page boundaries. A 236-page Act is 16 calls at roughly a second a page - about four minutes, inside the 600-second acknowledgement deadline on the push subscription.

The second number is the ceiling, 250 pages. Above it a request will not finish before Pub/Sub redelivers, so the document is queued for a batch job on the same image with no deadline. The order of the check was a bug once: the first version parsed the whole document and then looked at the count, paying for OCR it then discarded. Now the count comes off the page tree for nothing, before Document AI sees a byte. Batch processing takes 500 pages a request but is asynchronous, needs an output prefix and polling; a dozen online calls inside one request is simpler and was chosen deliberately.

Practical · Q5

How do you scan a corpus for personal data with Cloud DLP without hitting its quota, and what exactly do you store about a finding?

Scan per document, not per chunk, and never store the value. DLP bills per byte but meters requests per minute, and the first live load of DocuMind's corpus - one request per chunk from ten workers - was refused with Number of requests per minute. The fix is a packing loop: a document's chunks are joined with a blank line into requests of at most 400,000 bytes, under the 0.5 MiB an inspect request takes; each chunk's start offset is remembered; a finding's byte offset is mapped back to its chunk with a bisect. The 283-chunk handbook is one request; the ACME corpus is nineteen. A quota refusal is retried with backoff for up to five minutes rather than failing the document.

What is stored: the info type (one of seven India-first types - Aadhaar, PAN, GSTIN, e-mail, phone, name, date of birth), the likelihood, the offset inside the chunk, the chunk id. include_quote is false in every request, because a findings record that quotes the PAN it found has moved the PAN into the audit store, where it is hardest to delete. The scan runs before any row is written; a failed scan fails the message, because indexing an unscanned document is the thing the control exists to prevent.

Practical · Q6

What limits govern an embedding request, and how does the indexer batch under them?

Two limits per request for text-embedding-005: 250 texts, and 20,000 tokens across all of them; a request over either fails whole. The indexer's batches() closes a batch at 250 texts or when the next text would push its estimated tokens past 15,000 - a margin under the real limit, because tokens are estimated as characters divided by three, and a Hindi-English invoice or a table tokenizes worse than the estimate. The handbook's 283 chunks go up in four calls of 85, 78, 78 and 42 texts; the ACME corpus, 1,628 chunks, in 57 on the lane, which batches per document.

The response is validated as strictly as the request: one finite 768-dimensional vector per text, or the call raises. An empty list, a short vector, a NaN or an infinity all fail, and an offline test pins each case with a stubbed SDK. The client is regional - us-central1, because embeddings are not served from the global endpoint Gemini generation uses - and the model and version come from one Terraform variable read by the worker and the API alike. If pushed on the first live failure: it was the token limit on the long Acts, on 6 September 2026, and this function is the fix.

Practical · Q7

Walk me through how a re-issued document gets its vectors.

Three functions. held_vectors reads the source's current rows for this tenant - three equality filters: tenant, source URI, current - and keeps each row's vector under its chunk_hash, but only if the embedding stamp matches the configured model, version and task type. plan_carry_over is pure: for each new chunk it looks up the hash and returns the held vector or None, plus the list of misses. embed_with_carry_over embeds the misses only, slots the fresh vectors into the gaps, and returns two counts, reused and embedded, that ride on the claim record, the ledger row and the log line.

On the ACME handbook with one clause changed: 283 rows held, 281 hits, two misses - the changed clause and the preamble, whose title line changed - and one embedding call with two texts. Two boundaries worth stating: the lookup is by source, so the same paragraph under another object name is embedded again; and it is by tenant, so Zeta's copy of an Act never lends ACME a vector. The hash is computed on whitespace-collapsed text, so a re-wrapped paragraph is a hit and a changed figure is a miss. If asked what could go wrong: a row with a stale stamp is silently a miss, which is correct, and the counts on the log line are how you notice a whole document missing when it should have hit.

System design · Q8

Design tenant isolation in a shared vector index used by many tenants.

Isolation must be a property of the query, not a habit of the caller. Every datapoint carries a tenant_id restrict, and a restrict is a filter the index applies before it ranks: a query from ACME can only see ACME's points, whatever the caller forgot. DocuMind adds three more namespaces on every point - kind, doc_type, and current, always "true" - so a query can narrow to text or figures and the ANN tier agrees with the row store's current flag even before retired ids are removed.

Then scope every identifier. Datapoint ids and row ids are tenant:sha256#i; the version key is tenant_sha256. Without the tenant in the id, two tenants holding the same Act write the same ids and the last one wins - the failure DocuMind had on 7 September. Build the datapoint in one function used by ingest, undo and repair, so the three can never disagree about the restricts. Keep the sparse encoder shared between the document side and the query side, because a hybrid score across two hash spaces is noise. Treat the isolation rows of the golden set as release blockers: a leak is a data incident, not a quality regression. If pushed on "why not one index per tenant?": at a hundred tenants you pay for a hundred deployed indexes; restricts give the same guarantee on one, provided the id and the restrict are both tenant-scoped.

System design · Q9

Design the write path when the row store, the vector index and the warehouse share no transaction.

Accept that they do not, and design so every partial state is either invisible or repairable. First, ids: the Firestore row id, the Vector Search datapoint id and the BigQuery insert id are the same string, tenant:sha256#i, so a retry after any failure lands on itself - Firestore upserts, the index upserts, BigQuery de-duplicates on the insert id. Second, visibility: rows are written staged (current=false) and flipped in one pass after everything is in place, so a reader never sees half a version. Third, order: the index is written after the swap and the retired ids removed after that, with a current restrict on every point so a late removal does not surface an old version.

Fourth, repair: a job reads the current rows, re-embeds whatever the stamp says is stale, upserts to the index first, and only then checkpoints the vectors into Firestore with an optimistic-concurrency precondition on each row's last update time. A failed index write never marks a row migrated; a failed commit leaves the batch retryable; a row changed in between fails the commit instead of being overwritten. Fifth, honesty: the repair refuses to run in dry-run mode, because a dry run cannot checkpoint what it never published, and it runs in a maintenance window. If pushed - "why not a saga or an outbox?" - say the outbox is the claim record, and the compensations are cheap because nothing is ever deleted.

Trade-off · Q10

Layout Parser in the US gives you headings and tables; OCR in Mumbai gives you text. Which do you choose, and how do you defend it?

Residency first, quality second, and the choice is a configuration, not a habit. The Layout Parser returns document structure - headings, tables, reading order - which makes better chunks and citations, and it runs only in us. Enterprise OCR runs in asia-south1 and returns text with layout boxes, no semantic structure. For a customer whose contract, or whose reading of the DPDP Act, says personal data of people in India stays in India, the processor in the US is not available to you, whatever it would have given you. That is not a trade-off you get to make on quality grounds.

So the kit puts the choice in one variable, RESIDENCY, read by the parser and by Terraform from the same two-row map, and provisions exactly one processor. What you give up under india is structure, and the chunker compensates: a handbook is chunked by its Markdown headings regardless of processor, and a PDF is windowed per page so citations still carry a page. What you give up under us is the residency claim - and the deployment's own default is us, the Makefile's, not the module's, so the honest answer includes checking which one your lane runs. When pushed with "the customer will never know", say the audit trail records the processor location, and a residency promise you cannot evidence is a liability, not a feature.
