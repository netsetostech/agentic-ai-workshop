Ingesting: from an upload to a chunk you can search

A tenant drops a PDF into a bucket. A little later the same file is split into chunks, checked for personal data, turned into vectors and ready for a question - and when a corrected version arrives next month, only the paragraphs that changed are paid for. This lesson opens the worker that does all of it: code/services/ingest/, about 2,500 lines of Python, plus the six Terraform files that wire it in.

In plain words, ingesting is the part of DocuMind that turns a file into rows. Everything the search side (lesson 3.4) reads was written here. So this lesson has to answer the four questions every indexing pipeline has to answer: How does the system know a file is new? What if the same file arrives twice? What happens when a policy is re-issued? And how do you undo a bad update without paying for it again?

Architecture, and how Firestore is designed

The shape of the pipeline, the three names every document has, the collections and their fields, and the eight steps an update goes through.

The shape, in one paragraph

A file lands in the PROJECT-uploads bucket under its tenant's folder, for example acme/hr_policy_2026.md. The bucket announces it (a Cloud Storage notification into a Pub/Sub topic). A push subscription POSTs that announcement to a small Cloud Run service, documind-ingest. The worker downloads the exact version that was announced, checks it has not already been indexed, reads the text out of it (Document AI for PDFs, Gemini for pictures and video), scans it for personal data (Cloud DLP), cuts it into chunks, makes a vector for each chunk it has not seen before, and writes the chunks to Firestore and to the Vector Search index. Then it records what it did in a ledger and logs one line. Nothing here polls the bucket, and nothing here ever deletes a row: an old version is flagged, and a retention policy removes it a month later.

Three names for one document

The design rests on giving a document three separate identities, because they change at different times:

  • The source is the object path, acme/hr_policy_2026.md. It answers which document. Firestore ids cannot hold a slash, so the ledger stores it as acme~hr_policy_2026.md.
  • The version is the SHA-256 of the bytes: doc_key = acme_<sha256>. It answers which edition of that document. Same bytes, same key - which is exactly how a duplicate upload is caught.
  • The chunk has an id for citations, acme:<sha256>#7 (the version and the position), plus two fields that give it an identity across versions: chunk_hash, the SHA-256 of its text with the whitespace collapsed, and locator, where it sits - a clause code like NP-03, a page-and-window like p7-1, preamble, figure, or t0-60 for a video segment.

A path tells you which document. A hash tells you which version. A chunk hash tells you which paragraphs actually changed. Hold on to that sentence; the update logic below is nothing but those three facts used in order.

Two Terraform details make this design work. firestore_indexes.tf declares the vector indexes the reader needs - (tenant_id, embedding), (tenant_id, current, embedding) and the filter combinations - and it declares a TTL policy on chunks.expire_at. That policy is the only thing on the whole lane that ever deletes a chunk. The worker, the jobs and the Makefile never call delete.

How an update is handled: the eight steps

Suppose acme/hr_policy_2026.md is uploaded again with one clause changed. Same name, new bytes. Here is what happens, in order:

  1. Guard. Cloud Storage numbers every version of an object (its generation). The worker reads the ledger row for this path first: if the event's generation is older than the one already indexed, it is a late redelivery and is acknowledged with one log line, ingest_stale_event. Nothing is downloaded. Otherwise the bytes of exactly that generation are fetched - never "whatever the object holds now".
  2. Claim. documents/{doc_key} is written in a transaction. Only one worker can win it, so two deliveries of the same message, or two people uploading the same file, cannot index it twice.
  3. Parse, scan, chunk. A PDF goes to Document AI in 15-page slices (the online limit); a picture or video is described by Gemini instead; plain text needs no processor. One DLP scan covers the whole document. Then the text is cut: a handbook with ## headings gets one chunk per section (the clause code is the locator); anything else gets 2,000-character windows with a 200-character overlap, cut page by page so a chunk never straddles a page break.
  4. Carry-over. For every new chunk the worker looks for a current row of the same source with the same chunk_hash and the same embedding stamp. If it finds one, it copies the vector. Only the misses are embedded. For the handbook, that is 281 reused and 2 embedded.
  5. Stage. The new rows are written with current=false and staged=true. No reader can see them yet. They carry a one-day expire_at, so a stage that nothing ever swaps disappears by itself.
  6. Swap. In one pass, the new rows are flipped to current=true first, and then every other current row of that source is retired: current=false, superseded_by, superseded_at, and expire_at = now + 30 days. A reader between the two halves finds the new version, never none and never both. The Vector Search index follows: the new ids go up, the retired ids come out.
  7. Record. documents/ becomes indexed with the counts; sources/ gets the new ledger row (which version, which generation, what it cost); ledger/{tenant} gets a new fingerprint, which is what tells the caches to go stale. An audit event doc.upload is written, and one log line, ingest_ok, carries reused, embedded and retired.
  8. Later. After 30 days the TTL policy deletes the retired rows. Every night at 23:30 a reconcile job compares the bucket with the ledger, retires what left the bucket, re-ingests what changed behind its back, and prints one number: the drift.
What just happened

The 283-chunk handbook was re-issued with one clause changed. The worker's line read reused=281 embedded=2 retired=283: two embedding calls instead of 283, the old version flagged rather than deleted, and the caches told to refresh. That is what "pay for what changed" looks like in a log.

The undo, and the two status ladders

Upload the old bytes again and the worker recognises the doc_key of a version it retired. It does not re-embed anything: reactivate() counts the retired rows still on disk against the number the claim recorded and checks the retirement is inside the 30-day window. If both hold, the rows are flipped back to current, the newer version is retired in its turn, and the line says ingest_reactivated. If rows are missing or the window has closed, the undo is refused (reactivate_incomplete) and the bytes are ingested as a fresh version, with the carry-over reusing whatever the newer version still holds. A source a person took down on purpose (make retire) is a tombstone: withdrawn, and only make restore brings it back.

  • documents.status: processing (a worker holds it) → indexed (current) → superseded (retired, the undo window running) - or queued (waiting for the batch job) or failed (the error is on the row; the next delivery may retry).
  • sources.status: indexed (the current version is live), retired (the object left the bucket), withdrawn (a person took it down; the object is kept).
📋

The office notice board. A new notice is pinned over the old one. The old one is not torn up: it is stamped "replaced on 12 September" and put in the archive box, and the archive box is emptied after 30 days. Anyone reading the board sees only the current notice. If the new notice turns out to be wrong, the old one is still in the box and goes straight back up - no need to print it again.

Why the worker never reads "the object as it is now"

Push delivery is at-least-once and not in order. If someone uploads version 2 and then version 3 within a minute, the event for version 2 can arrive after version 3 has been indexed. The generation guard (step 3) throws that late event away, and fetching by generation guarantees that an event and its bytes are one version. Without those two rules, an old version could quietly become current again.

6.1 The message contract: the tenant is the folder

services/ingest/contracts.py
class IngestMessage(BaseModel):
    """The object record Cloud Storage publishes on object.finalized, as we choose to see it."""
    model_config = ConfigDict(populate_by_name=True)

    bucket: str
    name: str
    size: int = Field(ge=1)
    content_type: str = Field(alias="contentType")
    generation: str
    tenant_id: str = ""

    @field_validator("name")
    @classmethod
    def _no_traversal(cls, v: str) -> str:
        if ".." in v or v.startswith("/"):
            raise ValueError("object name escapes its prefix")
        return v

    @model_validator(mode="after")
    def _tenant_from_path(self):
        if not self.tenant_id:
            prefix, sep, rest = self.name.partition("/")
            if not sep or not prefix or not rest:
                raise ValueError("object is not under a tenant prefix")
            self.tenant_id = prefix
        return self
↔ SWIPE

Pub/Sub hands the worker whatever the publisher sent. Parsing it into a model at the edge means a bad message fails here, with a field name, instead of three functions later with a KeyError. The record carries no tenant; the first folder of the object path is the tenant, which is why upload.sh uses one prefix per tenant and why a file at the bucket root is refused.

6.2 Two ids from the content, never from the message

services/ingest/contracts.py
class DocumentContract(BaseModel):
    tenant_id: str
    sha256: str
    gcs_uri: str
    pages: int
    doc_type: str = "unknown"
    effective_from: str | None = None      # the date the document says it applies from
    schema_version: int = SCHEMA_VERSION

    @property
    def doc_key(self) -> str:
        return f"{self.tenant_id}_{self.sha256}"       # the version: same bytes, same key

    def chunk_id(self, i: int) -> str:
        return f"{self.tenant_id}:{self.sha256}#{i}"   # tenant-scoped, stable for citations


def chunk_hash(text: str) -> str:
    """The chunk's identity across versions: its text with the whitespace collapsed."""
    return hashlib.sha256(_WS.sub(" ", text).strip().encode("utf-8")).hexdigest()
↔ SWIPE

The Pub/Sub message id is stable across a redelivery, so it would catch a retry - but the same PDF uploaded twice is two messages with two ids, and that is the duplicate people actually create. A content hash catches both. The chunk id is tenant-scoped on purpose: until 7 September two tenants uploading the same Act overwrote each other's rows, and ACME lost every shared document to whichever tenant ingested it last.

        raise HTTPException(400, "unparseable message")   # it would fail the same way every time

    older = stale_generation(_db, msg.tenant_id, msg.name, msg.generation)
    if older:                                          # a late redelivery of an OLDER version
        log.info(json.dumps({"event": "ingest_stale_event", ...}))
        return {"status": "stale", "generation": msg.generation, "ledger_generation": older}

    blob = _gcs.bucket(msg.bucket).blob(msg.name, generation=int(msg.generation))
    content = blob.download_as_bytes()                 # the bytes of THAT generation
    doc = DocumentContract(tenant_id=msg.tenant_id, sha256=sha256_of(content),
                           gcs_uri=msg.gcs_uri, pages=0)

    if not claim(_db, doc.doc_key, doc.gcs_uri, doc.tenant_id):
        if status_of(_db, doc.doc_key) == "superseded":
            ...                                        # the undo - see 6.9
        elif status_of(_db, doc.doc_key) == "queued":
            return {"status": "queued_batch", "doc_key": doc.doc_key}
        else:
            return {"status": "duplicate", "doc_key": doc.doc_key}   # a 200 acks it

    try:
        return index_document(doc, msg, content)
    except IngestFailed:
        raise HTTPException(500, "ingest failed")         # Pub/Sub retries, then the DLQ
↔ SWIPE

Three answers, three meanings. A 400 says "this message can never be processed" - it is logged as ingest_poison, and after its attempts run out Pub/Sub parks it in the DLQ where make dlq reads it. A 200 is an acknowledgement, including for a stale event and a duplicate: those are successes, and retrying them would achieve nothing. A 500 says "try again later": the claim has already been given back, so the retry can take it.

6.4 The claim is a transaction

services/ingest/idempotency.py
def claim(db, doc_key, gcs_uri, tenant_id, retake=False) -> bool:
    """True if THIS caller may proceed, False if someone already did."""
    ref = db.collection("documents").document(doc_key)
    retakes = ("failed", "superseded") if retake else ("failed",)

    @firestore.transactional
    def _claim(tx) -> bool:
        snap = ref.get(transaction=tx)
        if snap.exists and snap.get("status") not in retakes:
            return False                   # somebody has it, or had it and finished
        tx.set(ref, {"gcs_uri": gcs_uri, "tenant_id": tenant_id,
                     "status": "processing", "claimed_at": firestore.SERVER_TIMESTAMP})
        return True

    return _claim(db.transaction())
↔ SWIPE

Read-then-write without a transaction is a race with a window of a few milliseconds - and Pub/Sub delivers duplicates concurrently, so that window gets hit. Two workers would both read "absent", both write, and the document would be ingested twice. Note that a claim that ended in failed can be retaken: on the first live load, every retry of a failed document was acknowledged as a duplicate and the document stayed failed for ever.

6.6 Chunking: by section when there is one, by window when there is not

services/ingest/main.py - _chunk(), trimmed
_SECTION = re.compile(r"^## +(.+?) *$", re.M)
_CODE = re.compile(r"^([A-Z][A-Z0-9]{0,7}(?:-[A-Z0-9]{1,6}){1,2})\b")   # NP-03, IT-SEC-04

def _chunk(text: str) -> list[dict]:
    heads = list(_SECTION.finditer(text.strip()))
    out = []
    if heads:                                          # a handbook: one chunk per section
        for n, h in enumerate(heads):
            title = h.group(1).strip()
            body = text[h.end(): heads[n + 1].start() if n + 1 < len(heads) else len(text)].strip()
            code = _CODE.match(title)
            key = code.group(1) if code else f"s{n + 1}"
            for k, (_, piece) in enumerate(_windows(f"{title}\n{body}")):
                out.append({"text": piece, "kind": "text", "page_start": None,
                            "locator": key + (f"-{k}" if k else ""), "section": title})
    else:                                              # anything else: 2,000-char windows, per page
        paged = "\f" in text
        for p, page in enumerate(text.split("\f"), 1):
            for k, (_, piece) in enumerate(_windows(page)):
                out.append({"text": piece, "kind": "text", "page_start": p if paged else None,
                            "locator": f"p{p}-{k}" if paged else f"w{k}", "section": None})
    for c in out:
        c["chunk_hash"] = chunk_hash(c["text"])        # identity across versions
    return out
↔ SWIPE

Why not always use fixed windows? Because one inserted line at the top of a handbook moves every window after it, and a re-issue that changed one clause would reuse none of its 92 windows. Chunking by section keeps a chunk's text identical when a paragraph above it changes, and that is what lets the carry-over reuse 281 of 283. The same two rules live in shared/documind_corpus.py, so a notebook that seeds the corpus mints the same chunk texts, hashes and locators as the worker.

6.8 Carry-over: reuse the vector when the text did not change

def held_vectors(db, doc, chunks_collection="chunks") -> dict[str, list[float]]:
    """Reuse a prior CURRENT dense vector only when the chunk hash and embedding stamp match."""
    out = {}
    query = (db.collection(chunks_collection)
             .where("tenant_id", "==", doc.tenant_id)
             .where("source_uri", "==", doc.gcs_uri)
             .where("current", "==", True))
    for snap in query.stream():
        row = snap.to_dict() or {}
        if row.get("chunk_hash") and document_embedding_matches(row):
            out[row["chunk_hash"]] = list(row["embedding"])
    return out


def embed_with_carry_over(db, doc, chunks):
    held = held_vectors(db, doc)
    vectors, misses = plan_carry_over(chunks, held)          # None where nothing matched
    fresh = embed_all([chunks[i]["text"] for i in misses]) if misses else []
    for i, vector in zip(misses, fresh):
        vectors[i] = vector
    return vectors, {"reused": len(chunks) - len(misses), "embedded": len(misses)}
↔ SWIPE

document_embedding_matches() checks four things on the old row: same model, same version, task type RETRIEVAL_DOCUMENT, and a finite 768-dimensional vector. Any mismatch means the old vector could not serve this worker's queries, so it is not reused. embed_all() sends the misses to text-embedding-005 in batches of at most 250 texts and about 15,000 tokens, and refuses a response that is not one vector per text. The two numbers it returns are the ones on every log line.

6.12 The undo, verified before anything is flipped

The one rule to remember

Nothing on this lane deletes, and nothing on this lane guesses. A version is its bytes' hash, a chunk's identity is its text's hash, an event is fetched by its generation, and the only thing that removes a row is a retention policy you declared in Terraform. If you keep those four, an update costs what changed, is invisible until it is whole, and can be undone for free.
