Where ingest sits on the master diagram

The uploads bucket in, the four stores out, and the six readers that depend on what the worker wrote.

On DocuMind's master diagram (Module 1) the ingest lane is the left-hand journey, upload to index. One bucket feeds it. One Cloud Run service does the work, with two Cloud Run jobs on the same image beside it. Four stores come out: Firestore (the truth and the fallback index), Vector Search (the ANN tier), BigQuery (the SQL mirror) and, for tenants whose policy allows it, the managed stores. Everything the question-to-answer journey reads was written here.

Four things on this bucket matter to the lane. Versioning makes a generation fetchable: the worker downloads the bytes of the generation the event names, never "the object as it is now" (lesson 3.1's guard). The region is var.india_region, asia-south1, so the documents rest in Mumbai whatever region the services run in. The lifecycle moves an object to Nearline after 90 days and deletes it after a year - and an object the bucket deletes is a source the nightly walk retires. The tenant prefix is not a Terraform resource: it is a convention the worker enforces. The first folder of the path is the tenant (contracts.IngestMessage), an object at the bucket root has none and is refused as poison, and evals/upload.sh puts one prefix per tenant. Three accounts touch the bucket: the UI's writes (objectAdmin), the API's may only create (objectCreator, for the signed URLs), the worker's reads (storage.objectViewer in sa.tf) and never writes.

Where the docs and the code disagree: five attempts or twelve

README.md ("five attempts, then the DLQ"), the header comment of eventarc.tf itself ("a floor of five attempts"), the make poison and make dlq comments in the Makefile, the comment in main.py's poison branch and the v4 course plan all say five. The resource says max_delivery_attempts = 12, and the resource is what Terraform applies. Twelve is the number, and it changes what you should expect: with a 10 s backoff doubling to a 600 s ceiling, a message that fails every time reaches the dead-letter topic closer to an hour after the first refusal than to the "few minutes" the Makefile promises. Run make dlq later than you think, or read deliveryAttempt on the push subscription in the meantime.

The HTTP-code rule

Pub/Sub push has one rule: a 2xx acknowledges, anything else is a negative acknowledgement, retried under the policy above until the twelfth attempt, then parked on the dead-letter topic. The worker uses three answers. 200 for everything that is finished, including the early exits of step 4 - a stale event, a duplicate, a queued document, a withdrawn source, an undo. Retrying those would achieve nothing. 500 for a failure the next attempt may fix: the claim has been given back first (release()), so the retry can take it. 400 for a message the worker can never parse, logged as ingest_poison. Pub/Sub does not treat the 400 differently from the 500 - both are nacks, both walk the twelve attempts to the DLQ - the difference is for the people and the pager: ingest_poison is not ingest_failed, and the Ingest failed policy of step 8 does not page for a zero-byte object. The comment above the 400 in main.py says "ack the poison"; the code returns a 400, a 400 is a nack, and the DLQ is where the poison ends after its attempts - which is what make poison then make dlq shows.

📦

The courier's twelve visits. A courier with a registered parcel knocks, and if nobody answers he does not throw it away - he comes back after ten minutes, then twenty, then forty, and after the twelfth failed visit the parcel goes to the returns desk with a slip that says how many times he tried. The returns desk is ingest-dlq-sub, the slip is deliveryAttempt, and a locked door during a cold start is not the parcel's fault - which is why twelve, not five.

The update path, with every early exit

The eight steps of lesson 3.1 drawn as the worker walks them, and every branch that answers 200 before the end.

Lesson 3.1 listed the eight steps an update goes through. Here they are as the code walks them - push() for the first two and the undo, index_document() for the rest - with the side roads. Read the spine top to bottom for the ordinary case, one object under an existing name with new bytes; read the amber boxes for the six ways a delivery ends early and correctly.

The push handler, step by step
1
Guard. push() parses the envelope into IngestMessage. stale_generation() reads sources/{tenant~name} and compares generations. The bytes of that generation are downloaded.
Unparseable: ingest_poison, 400. Older than the ledger: ingest_stale_event, 200, nothing downloaded. Generation gone (overwritten): the same line with a second reason, 200 - the newer generation's own event indexes it.
2
Claim. sha256_of(content) gives the doc_key; claim() writes documents/{doc_key} in a transaction. Then current_chunks() asks whether this version is already current.
Claim lost, status superseded: step 7. Status queued: queued_batch, 200 - the batch lane holds it. Anything else: ingest_duplicate, 200. Claim won but rows already current with the full embedding stamp: ingest_already_current, 200 - the ledger learns the generation, nothing parsed.
3
Parse, scan, chunk. A picture or a video is described by Gemini (_describe_media) and its pixels DLP-scanned. A PDF is counted by pypdf before Document AI sees it, then parsed in 15-page slices by residency; text/* is decoded as it is. effective_from_of() reads the date, _chunk() cuts by section or by 2,000-character window, inspect_many() scans once per document; findings go to dlp_findings and the dlp.finding audit event.
Over MAX_INLINE_PAGES (250) on the push lane: _enqueue_batch() writes ingest_batch/{doc_key}, sets the claim to queued, starts the batch job if BATCH_JOB names one, logs ingest_queued_batch with the consumer, 200. No OCR is paid for.
4
Carry-over. embed_with_carry_over(): held_vectors() reads the source's current rows whose stamp matches, plan_carry_over() matches by chunk_hash, embed_all() sends only the misses - batches of 250 texts or 15,000 tokens, text-embedding-005, RETRIEVAL_DOCUMENT, 768 dimensions, regional client.
A first version: nothing held, everything embedded. Legacy rows without the task stamp: never reused, whatever their hash says.
5
Stage. mirror_to_firestore(staged=True): every row lands current=false, staged=true with expire_at one day out, in batches of 400. No reader can see them.
A stage nothing swaps - the worker died between 5 and 6 - is deleted by the TTL policy within about a day of the stamp. The retry re-stages with the same ids.
6
Swap. swap_versions() flips the new rows current and clears the stage marks, then retires every other current row of the source: superseded_by, superseded_at, expire_at = now + 30 days, effective_to. The old claim becomes superseded with retired_at. Then upsert() the new datapoints, remove_datapoints() the retired ids, the managed mirror's after_swap(), the BigQuery rows.
More than 400 rows: two commits, and for a moment two versions are current. The reader's newest-per-source guard (step 7) is what makes that window invisible.
7
The undo (reached from step 2). The same bytes again after a newer version retired them. reactivate() counts the retired rows against the claim's chunks and retired_at against RETENTION_DAYS, then flips them back; reupsert() puts their ids back in the ANN tier before retire_previous() takes the newer version out; after_undo() follows; record_source() with embedded=0.
Withdrawn (make retire): ingest_withdrawn, 200, nothing moves. Short or old: reactivate_incomplete with both numbers, the claim retaken with retake=True, and the bytes go through step 3 as a fresh version. Otherwise: ingest_reactivated, 200.
8
Record. finish() (the claim: indexed, chunks, reused, embedded, generation), record_source() (the ledger row), refresh_fingerprint() (ledger/{tenant}, and a ledger_fingerprint line), ingest_superseded when anything was retired, the doc.upload audit event, and ingest_ok with reused, embedded, retired. 200.
Anything threw between 3 and 8: release() sets the claim failed with the error text, ingest_failed is logged, the handler answers 500, Pub/Sub retries, the next delivery may retake a failed claim, and the twelfth failure is the DLQ.
A side road: an early 200, a hand-off, or the failure path

Six early exits answer 200 on purpose - stale, duplicate, queued, already current, withdrawn, reactivated - because each is a finished state a retry could only repeat. The only 500 is a real failure with the claim already given back. Lesson 3.4 reads the functions; lesson 3.5 makes every branch happen.

The stores, in write order

Seven writes, in the order the code makes them, and the Terraform file that created each place they land.

The order matters, because a worker can die between any two lines and the design depends on what the reader sees at that moment. Firestore is written first and staged, so nothing is visible until the swap; the ANN tier follows the swap, so an index datapoint never points at a row that is not current; the mirrors and the ledger come after, so a failure in them never leaves a half-visible version. INDEXING.md section 2 folds the mirror into the swap step and does not mention BigQuery; the table is index_document() as it runs.

Three details to carry. The mirror asks per document whether the tenant may leave India: tenant_settings/{tenant}.data_region is in (or absent, which fails closed) or any, read once a minute; a forbidden store is one mirror_policy_skipped line per tenant and store, then silence; a copy is mirror_ok, no store is mirror_no_store, an error is mirror_failed - none fails the ingest. The BigQuery insert names its row ids after the chunk ids, so a retried delivery does not double the table. And the fingerprint is the SHA-256 of the tenant's sorted current doc_keys: README.md still says the cache record is "dropped"; the code writes the fingerprint into ledger/{tenant}, touches no cache record, and the API notices the mismatch on its next question (step 7).

What just happened

One delivery became seven writes, and each one was placed where a crash between it and the next leaves the reader with exactly one version. The rows that will be searched were written invisible, made visible in one pass, then announced to the ANN tier, the mirrors, the ledger and the log - in that order, never the reverse.

services/rag-api/retriever.py - newest_per_source() and prefer_current()
def newest_per_source(chunks: list[dict]) -> list[dict]:
    # ...
    newest: dict = {}
    for c in chunks:
        src, key = c.get("source_uri"), c.get("doc_key")
        at = c.get("reactivated_at") or c.get("indexed_at")
        if not (src and key and at is not None):
            continue
        if src not in newest or at > newest[src][1]:
            newest[src] = (key, at)
    return [c for c in chunks
            if not (c.get("doc_key") and c.get("source_uri") in newest and c["doc_key"] != newest[c["source_uri"]][0])]

def prefer_current(chunks: list[dict]) -> list[dict]:
    # ...
    return newest_per_source([c for c in chunks if c.get("current") is not False])
